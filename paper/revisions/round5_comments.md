## Summary
This paper designs, formally specifies, implements, and evaluates a monolithic eBPF/XDP/TC gateway data plane that integrates a stateful L2/IPv4 firewall, a Layer-4 load balancer with bidirectional DNAT/SNAT and graceful backend draining, and per-flow telemetry in a single verified program without tail-call chaining. Controlled at runtime by a Python control plane via shared BPF maps and a REST API, the pipeline uses a read-only reply pre-classifier to evaluate firewall admission rules over the client-visible Virtual IP (VIP) flow in both directions while mutually recovering evicted forward and reverse NAT LRU entries. In this revised manuscript, the authors have thoroughly addressed the previous review comments—integrating the native Linux software flowtable (`nft-FT`) baseline, the 1,000-rule (`+rules`) macro-benchmarks, the shared-metadata tail-call ablation, the new-UDP DNAT microbenchmark, and intermediate cache-cold flow points, while resolving the formal state-coupling edge cases and reconciling all test counts (142 of 143 automated tests passing) and paired $t$-test analyses.

## Strengths
* **Thorough Resolution of Prior Review Feedback and Comprehensive Stateful Benchmarking:** All previously omitted baselines (`nft-FT`), populated-rule macro-benchmarks (`+rules`), and microbenchmark ablations (shared-metadata tail calls, new-UDP DNAT probes, and 1k/15k cache-cold flows) have been completely integrated across Tables II–V and Figures 2–17. Comparing the eBPF pipeline directly against Linux's native software flowtable (`nf_flow_table`), `nftables` with `IPVS`, and stateful Open vSwitch (`OVS-ct`) under both empty and populated rule tables yields a valuable architectural insight: amortizing established-flow processing into a single-lookup verdict/flow cache matters more for sustained gateway throughput than hook placement or eliminating tail calls.
* **Rigorous Formal Specification and Verification of Coupled Firewall and NAT State:** The mathematical model and pipeline algorithms cleanly formalize read-only reply pre-classification over the client-visible VIP flow, backend endpoint isolation, and mutual LRU state recovery, and have been soundly updated to evaluate exact priority-ordered rule decisions during state flushing and first-fragment inspection as well as TCP `SYN` client-port reuse. This formal rigor is backed by 143 automated unit and dual-hook `BPF_PROG_TEST_RUN` kernel packet tests (verifying incremental checksum rewrites and regression edge cases) alongside end-to-end Mininet validation.

## Weaknesses
* **Incremental Architectural Novelty and Per-Packet Lookup Overhead Without a Verdict Cache:** Combining stateful firewalling, DNAT/SNAT load balancing, and LRU state recovery into a single eBPF program represents an incremental refinement over existing production and academic systems that already provide these capabilities or automate post-verification merging and runtime specialization, while re-evaluating up to ten fixed whole-field hash tables on every packet (224–270 ns when all patterns are populated) causes the pipeline to trail single-lookup flow caches (`nft-FT` by 11–25% and `OVS-ct` by 6–14% under populated rules) (Reference Paper: Cilium: eBPF-based Networking, Observability, and Security, Cilium Authors, 2025; Reference Paper: A Framework for eBPF-Based Network Functions in an Era of Microservices, Sebastiano Miano et al., 2021; Reference Paper: Verified Programs Can Party: Optimizing Kernel Extensions via Post-Verification Merging, Hsuan-Chi Kuo et al., 2022; Reference Paper: Domain Specific Run Time Optimization for Software Data Planes, Sebastiano Miano et al., 2022; Reference Paper: Netfilter's Flowtable Infrastructure, Pablo Neira Ayuso / Linux Kernel Community, 2026; Reference Paper: Revisiting the Open vSwitch Dataplane Ten Years Later, William Tu et al., 2021).
* **Pre-Fix Performance Measurements and In-Kernel Microbenchmark Variance:** As noted in Section V-C, the regression fixes for reused TCP client ports, timestamp-ordered reverse-entry recovery with in-place refresh, and exact-decision state flushing were applied after the Section VI measurements were collected, leaving a minor discrepancy between the verified post-fix program and the benchmarked binary. In addition, sequential batch execution in `BPF_PROG_TEST_RUN` exhibits 30–106 ns shifts across identical code paths (such as the elevated 115.1 ns 1-rule XDP repeat-loop pass baseline and the 275.5 ns single-shot XDP SNAT figure), which is large relative to the 46–67 ns tail-call ablation differences.
* **Emulated `veth` Testbed Limitations and Minor VIP Rule-Hook Asymmetry:** Running all macro-benchmarks over in-memory `veth` pairs within a single host kernel with checksum and segmentation offloads disabled means packets already carry an allocated `sk_buff` and execute in the sender's softirq context, preventing evaluation of driver-level XDP execution. Furthermore, in the `+rules` workload for `nft+IPVS`, placing the 1,000 `nftables` set lookups only in the `forward` chain causes VIP traffic (which IPVS processes from the `input` hook) to bypass the firewall rule sets.
* **Minor Residual State-Coupling Corner Cases on TCP `SYN` Port Reuse:** In Section III, if a new TCP `SYN` reuses a client port after $\mathcal{L}[f]$ was evicted and selects a new backend while an older $\mathcal{T}_{rev}$ entry remains unexpired, a late reply from the old backend can still match $\mathcal{T}_{rev}$ directly unless cross-checked against $\mathcal{L}[f]$, and restarting $\mathcal{L}[f]$ on a draining backend without prior `FIN`/`RST` does not explicitly reset the corresponding $\mathcal{T}_{fw}$ entry's creation timestamp.

Only two narrow residual boundary considerations remain in the updated state-coupling specification for TCP `SYN` port reuse:

1. **Potential Concern: Leftover $\mathcal{T}_{rev}$ Entry When a Port-Reusing TCP `SYN` Arrives After $\mathcal{L}[f]$ Eviction (Sections III-E and III-F, Pages 4–5)**
   * **Observation:** Under *Stickiness and graceful draining* (Section III-E, p. 4, right column), when a new TCP `SYN` (without `ACK`) reuses the client port of an earlier connection while $\mathcal{L}[f] = (b_{\text{old}}, j_{\text{old}})$ is still present in $\mathcal{L}$ (and has seen `FIN`/`RST` or $b_{\text{old}}$ is draining), the gateway knows $b_{\text{old}}$ from $\mathcal{L}[f]$ and explicitly deletes the old reverse entry $\mathcal{T}_{rev}[r_{b_{\text{old}}}(f)]$ before inserting the new entries (consistent with Algorithm 2, lines 17 and 21–22). However, under *Coupling and recovery* (Section III-F, pp. 4–5, first bullet), if $\mathcal{L}[f]$ was already evicted from its LRU map (or deleted first by the reaper while $\mathcal{T}_{rev}[r_{b_{\text{old}}}(f)]$ remained present), a new TCP `SYN` skips the 16-slot $\mathcal{T}_{rev}$ probe (*"If $\mathcal{L}[f]$ is missing and the packet is not a TCP SYN, it probes $\mathcal{T}_{rev}[r_{b_i}(f)]$... A SYN always opens a new connection, so it is placed by Eq. (6) and cannot be captured by a leftover reverse entry"*).
   * **Potential Concern:** If Eq. (6) places this new `SYN` onto a *different* backend $b_{\text{new}} \ne b_{\text{old}}$ (for instance, because $b_{\text{old}}$ was drained while $\mathcal{L}[f]$ was evicted), $\mathcal{T}_{rev}[r_{b_{\text{old}}}(f)]$ is neither probed nor deleted, so $\mathcal{T}_{rev}[r_{b_{\text{old}}}(f)]$ and $\mathcal{T}_{rev}[r_{b_{\text{new}}}(f)]$ coexist until the old entry expires. While the "most recently seen" rule protects forward recovery as long as $\mathcal{T}_{rev}[r_{b_{\text{new}}}(f)]$ is newer, a late packet arriving from $b_{\text{old}}$ (such as a retransmitted `FIN`/`ACK` or `RST`) during that window will match $\mathcal{T}_{rev}[r_{b_{\text{old}}}(f)]$ directly in the reply path (Section III-F, p. 5, second bullet), be SNAT-forwarded to the client, and refresh $\mathcal{T}_{rev}[r_{b_{\text{old}}}(f)]$'s timestamp $\tau_\ell$ without verifying whether an existing $\mathcal{L}[(c, v, p_c, p_v, \pi)]$ currently points to a different slot $j_{\text{new}} \ne j_{\text{old}}$. Briefly noting this post-eviction corner case—or having reply classification verify, when $\mathcal{L}[(c, v, p_c, p_v, \pi)] = (b, j')$ is present, that its slot $j'$ matches the slot $j$ recorded in $\mathcal{T}_{rev}[f(x)]$—would make the state-coupling specification completely airtight.

2. **Potential Concern: Alignment of $\mathcal{T}_{fw}$ Entry Restart With $\mathcal{L}[f]$ Restart on a Draining Backend Without Prior `FIN`/`RST` (Sections III-D and III-E, Page 4)**
   * **Observation:** Section III-E (p. 4, right column) specifies that $\mathcal{L}[f]$ and $\mathcal{T}_{rev}$ are restarted on a new TCP `SYN` (without `ACK`) if the stored connection has seen `FIN`/`RST` **or** its backend is draining ($\alpha_j = 0$), whereas Section III-D (p. 4, left column) states that the firewall connection tracker $\mathcal{T}_{fw}$ restarts its entry on a TCP `SYN` (without `ACK`) when the existing entry *"has seen FIN or RST"* (consistent with Algorithm 1, line 27, which does not receive the `restart` condition from `LOADBALANCE`).
   * **Potential Concern:** If an earlier connection to a VIP terminated silently without `FIN`/`RST` while its backend was placed into draining mode ($\alpha_j = 0$), and the client reuses the same source port for a new TCP `SYN` before $T_{\text{idle}}$ expires, $\mathcal{L}[f]$ and $\mathcal{T}_{rev}$ start afresh on an active backend, whereas the entry in $\mathcal{T}_{fw}$ (having recorded neither `FIN` nor `RST`) is refreshed in place rather than restarted, retaining the earlier connection's creation timestamp $\tau_c(e)$ for hard-timeout evaluation ($T_{\text{hard}}$ in Eq. (9)) and its `REPLY` mark. Clarifying whether $\mathcal{T}_{fw}$ also restarts its entry whenever `LOADBALANCE` restarts $\mathcal{L}[f]$ on a draining backend would align the lifecycle reset semantics across all three state tables.

1. **Performance Measurements Collected Prior to Post-Measurement Data-Plane Regression Fixes (Section V-C, Page 8; Section VI-E, Page 12):**
   - **Potential Concern:** In Section V-C (*"Correctness Methodology"*, page 8, right column), the authors transparently note:
     > *"The fixes for reused ports, recovery and flushing were made after the measurements of Section VI; they change only those rare cases and the control plane, and add no more than a flag test to the paths measured there."*

     While control-plane state-flushing changes affect only rule-insertion operations, comparing Algorithm 2 (page 6) and Section III-D/F (page 4) against the timed paths in Section VI indicates that the data-plane fixes modify per-packet eBPF code executed during the benchmarks:
     - **Established VIP Forward Path (`DNAT est.` and VIP macro-benchmarks):** Line 17 of Algorithm 2 adds the `restart` check (`syn` flag check, evaluation of stored TCP `FIN`/`RST` flags in $\mathcal{L}[f]$, and a lookup of the backend active flag $\alpha_j$ in `lb_backends`) before taking the established forward branch at line 18, and Section III-D adds a corresponding `SYN` after `FIN`/`RST` check when updating $\mathcal{T}_{fw}$.
     - **New UDP Flow Path (`DNAT new UDP` in Table V and Fig. 17) and Eviction Recovery:** Because a new UDP flow to a VIP is not a TCP SYN and misses $\mathcal{L}[f]$, it traverses the $n$-slot reverse-table recovery probe loop at lines 23–26 of Algorithm 2 before falling through to `SELECT(f)`. The post-measurement fix modified this loop to scan all $0 \le i < n$ slots and compare `last_seen` timestamps $\tau_\ell$ to select the most recently seen slot, and added a map update at line 25 to refresh $\mathcal{T}_{rev}[r_{b_i}(f)]$.
     - **Microbenchmark Sensitivity and Artifact Consistency:** As documented in Section VI-E (page 12), the `BPF_PROG_TEST_RUN` microbenchmarks exhibit a ~30 ns repeat-loop and ~100 ns single-shot reproducibility floor even when the C source is unchanged, as small shifts in loop structure, instruction layout, or register allocation from `clang -O2 -target bpf` can alter cache alignment or stack spills. Reporting performance measurements from a pre-fix binary leaves a minor disconnect between the formally specified and verified program (passing 142 of 143 tests) and the benchmarked binary.
   - **Suggested Improvement:** Re-run at least the automated in-kernel `BPF_PROG_TEST_RUN` microbenchmark suite (`microbench.json`, reported in Table V and Figs. 3, 14–17)—which executes quickly on a single core without Mininet orchestration—on the final post-fix eBPF binary, or add a brief spot-check note in Section V-C confirming that the compiled instruction count and `BPF_PROG_TEST_RUN` latencies of the final post-fix binary remain within the stated confidence intervals.

2. **Microbenchmark Repeat-Loop Baseline Variance, Single-Shot Timing Overhead Estimation, and Sequential Batch Drift (Section VI-E, Pages 12–13; Fig. 3, Table V, and Fig. 15):**
   - **Potential Concern:** Section VI-E candidly documents noticeable run-to-run variability in `BPF_PROG_TEST_RUN` even on a pinned performance core (CPU 0) under the `performance` governor, which affects both the single-shot overhead estimate and specific comparisons in Table V, Fig. 3, and Fig. 15:
     1. *Elevated 1-rule XDP repeat-loop baseline and single-shot overhead estimate:* In Section VI-E (*"Processing paths"*, page 12, right column), the constant per-syscall timing overhead of single-shot runs is estimated as single-shot minus repeat-loop `Pass` cost from Table V (measured with one installed rule), yielding **38 ns** at XDP ($153.0 - 115.1\text{ ns}$) and **86 ns** at TC ($180.6 - 95.1\text{ ns}$). This 38 ns estimate is then subtracted from the denominator in the tail-call ablation (*"Tail-call ablation"*, page 12) to compute the overhead-adjusted penalty (`+40%` on pass and `+38%` on DNAT). However, cross-checking Table V against *"Rules and connections"* (page 12, left column, and Fig. 3) shows that the empty-table (0-rule) repeat-loop cost is **68 ns** at XDP and **78 ns** at TC, and each populated pattern adds ~16–20 ns. With 1 installed rule (1 populated pattern), TC's repeat-loop pass cost in Table V (`95.1 ± 0.6 ns`) rises by 17 ns as expected, whereas XDP's repeat-loop pass cost jumps by 47 ns to **`115.1 ± 12.7 ns`**—20 ns *slower* than TC with a wide confidence interval, despite XDP being faster than TC across the rule sweep in Fig. 3. Conversely, comparing the 0-rule single-shot 1-flow baseline in *"Cache-cold state"* (`132 ns` at XDP and `120 ns` at TC, page 12) against the 0-rule repeat-loop baseline (`68 ns` at XDP and `78 ns` at TC) yields a single-shot syscall overhead of **64 ns** at XDP and **42 ns** at TC.
     2. *Sequential batch shifts across single-shot and repeat-loop phases:* In Table V (page 13) and Fig. 14 (page 16), single-shot `SNAT est.` at XDP measures `275.5 ± 13.3 ns` (making it appear 58 ns slower than `DNAT est.` at `217.4 ± 4.3 ns`, 79 ns slower than `TC SNAT est.` at `196.8 ± 4.7 ns`, and 18–19 ns slower than the 3-stage tail-call chains `Chain^a` and `Chain^b`), whereas it measured `169 ns` in the previous run on the identical code path (a `106 ns` shift). Similarly, in Fig. 3 (right, page 13), repeat-loop `TC` measures `106 ns` at `0` tracked connections and `95 ns` at `1k` connections before dropping to `78–79 ns` at `10k` and `60k` connections, and in Fig. 15 (page 16), single-shot `XDP` spikes to `524 ± 61 ns` at `15k` flows before dropping to `455 ns` at `60k` flows. A `30–106 ns` shift between contiguous batches of identical code is large relative to the `46–67 ns` tail-call ablation differences being evaluated in Table V. On a mobile Intel Core i7-1355U processor, collecting all samples of each point in sequential blocks can expose individual batches to P-core turbo power-limit (PL1/PL2) adjustments or activity on the sibling SMT thread (CPU 1) while still yielding tight within-batch confidence intervals.
   - **Suggested Improvement:** Briefly note in Section VI-E that the `115.1 ± 12.7 ns` XDP repeat-loop `Pass` measurement in Table V reflects the ~30 ns upward variance (which compresses the apparent $153.0 - 115.1 = 38\text{ ns}$ single-shot overhead relative to the $132 - 68 = 64\text{ ns}$ empty-table 1-flow baseline), and consider interleaving the `BPF_PROG_TEST_RUN` batch measurements across variants (`XDP`, `TC`, `Chain^a`, `Chain^b`) or locking the P-core clock frequency to a fixed sustainable non-turbo frequency with the sibling SMT thread (CPU 1) offlined during microbenchmarks.

3. **Hook-Placement Asymmetry of the `+rules` Firewall Workload on the VIP Path for `nft+IPVS` (Section V-A, Page 8; Section VI-C and Table IV, Page 11):**
   - **Potential Concern:** In Section V-A (*"Populated rule tables"*, page 8), 1,000 non-matching drop rules are installed to evaluate rule-scaling overhead on both the routed path and the VIP path. In Section VI-C (page 11, right column), the authors observe that `nft+IPVS +rules` loses $31.7 \pm 6.1\%$ of TCP throughput and $30.7 \pm 4.5\%$ of packet rate on the routed path, whereas its VIP path is not affected significantly ($8.76 \to 8.15\text{ Gbit/s}$, $p \ge 0.11$) *"because IPVS forwards VIP traffic from the input hook and the rule sets in the forward chain do not see it."*
   - **Methodological Implication:** Because IPVS hooks into `NF_INET_LOCAL_IN` (`input`) rather than `NF_INET_FORWARD` (`forward`), placing the 1,000 `nftables` set rules only in the `forward` chain means that `nft+IPVS +rules` does not evaluate the 1,000-rule firewall policy on VIP traffic—unlike `TC +rules`, `TC+FIB +rules`, `nft-FT +rules`, and `OVS-ct +rules`, all of which enforce the 1,000 rules against VIP connections. To enforce the same client-to-VIP firewall policy in `nft+IPVS`, those `nftables` set lookups would also need to be traversed by VIP packets (e.g., in `prerouting` or `input` prior to IPVS).
   - **Suggested Improvement:** Explicitly note in Section V-A and in a footnote to Table IV that `nft+IPVS +rules` bypasses the 1,000 rules on the VIP path due to `forward`-chain placement, so readers do not interpret the `nft+IPVS +rules` VIP columns in Table IV as an apples-to-apples rule-evaluation comparison.

4. **Reconciliation Between Section VI-C Narrative and Figure 10 for the Paired Comparison Against `Kernel` (Section VI-C, Page 11 vs. Figure 10, Page 15):**
   - **Potential Concern:** In Section VI-C (*"Cost of state relative to routing"*, page 11, left column), the narrative states that across all 10 rounds (including Round 8, where `Kernel` TCP throughput dropped to the `5.5 Gbit/s` outlier), *"only nft+IPVS is significantly slower in TCP ($-20.3 \pm 13.5\%, p = 0.008$)"*, and after reporting the 9-round sensitivity check notes that *"nft-FT, whose established flows bypass routing, is not slower than plain routing ($+6.1 \pm 7.6\%, p = 0.10$)."* However, in Figure 10 (*"Paired difference to Kernel"*, page 15), the plotted 95% paired-$t$ confidence interval for `nft+IPVS` TCP throughput appears centered near $-13\%$ and visibly crosses zero (extending from roughly $-35\%$ to $+10\%$, which corresponds to $p > 0.05$ when the Round 8 outlier where `nft+IPVS` exceeds `5.5 Gbit/s` is included in $100\,(a_r/b_r - 1)$), while the `nft-FT` TCP bar is near $+20\%$ with a wide confidence interval (reflecting the 10-round mean skewed by the Round 8 `Kernel` outlier, whereas $+6.1 \pm 7.6\%$ in the text is the 9-round value excluding Round 8).
   - **Suggested Improvement:** Verify whether $-20.3 \pm 13.5\%$ ($p = 0.008$) for `nft+IPVS` vs. `Kernel` and $+6.1 \pm 7.6\%$ ($p = 0.10$) for `nft-FT` in Section VI-C are from the 9-round comparison (or unpaired comparison) whereas Figure 10 plots all 10 rounds, and clarify in Section VI-C and the caption of Figure 10 which numbers include or exclude the Round 8 `Kernel` outlier.
