# HIGH LEVEL SUMMARY
---
## Summary
This paper designs, formally specifies, implements, and evaluates a monolithic eBPF/XDP/TC gateway data plane that integrates a stateful L2/IPv4 firewall, a Layer-4 load balancer with bidirectional DNAT/SNAT and graceful backend draining, and per-flow telemetry without tail-call chaining. The data plane is managed at runtime by a Python control plane via shared BPF maps and a REST API, enforcing firewall policy over the client-visible Virtual IP (VIP) flow in both directions while mutually recovering evicted forward and reverse NAT LRU entries. The authors validate functional correctness through automated unit, kernel, and Mininet tests, and evaluate performance against plain Linux routing, native Linux stateful subsystems (`nftables` and `IPVS`), and Open vSwitch (`OVS` and `OVS-ct`) across interleaved macro-benchmarks on emulated `veth` links and in-kernel microbenchmarks.

## Strengths
* **Clean Formal Specification of Coupled Firewall and NAT Semantics:** The paper provides a clear, self-contained mathematical model that tightly couples firewall admission, NAT state recovery, and graceful backend draining within a single verified eBPF pipeline. In particular, formulating a read-only reply pre-classifier so that firewall rules are evaluated strictly against the client-visible VIP flow in both directions—while enforcing backend endpoint isolation and mutual LRU state recovery—is a well-engineered architectural refinement.
* **Rigorous Verification and Like-for-Like Stateful Benchmarking:** The implementation is thoroughly validated across unit tests, dual-hook `BPF_PROG_TEST_RUN` kernel packet tests (verifying incremental checksum rewrites and regression edge cases), and end-to-end Mininet scenarios. Furthermore, comparing the eBPF pipeline directly against *stateful* Open vSwitch (`OVS-ct`) and native kernel connection tracking (`nftables` + `IPVS`) provides a more realistic and informative reference than comparing solely against stateless forwarding baselines.

## Weaknesses
* **Omission of Explicitly Configured Baselines and Ablations from Results:** Although the methodology in Sections II and V explicitly defines `nft-FT` (Linux `nf_flow_table` ingress offload as the native kernel fast-path counterpart to `TC+FIB`), five `+rules` macro-benchmark variants (1,000 rules across all ten patterns), and a shared-metadata tail-call ablation variant, their empirical results are completely omitted from all result tables and figures (Tables II–V, Figs. 2–17). Please consider reporting these omitted experiments, as `nft-FT` is required for an apples-to-apples fast-path comparison with `TC+FIB`, the `+rules` macro-benchmarks are needed to evaluate end-to-end throughput when all ten hash tables are probed rather than skipped by the empty-table bitmask, and the shared-metadata tail-call variant is necessary to separate intrinsic `bpf_tail_call` overhead from redundant packet re-parsing across stages (Reference Paper: A Framework for eBPF-Based Network Functions in an Era of Microservices, Sebastiano Miano et al., 2021; Reference Paper: Netfilter's Flowtable Infrastructure, Pablo Neira Ayuso / Linux Kernel Community, 2026).
* **Incremental Architectural Novelty and Trade-offs of Monolithic Design and Fixed Tuple Matching:** Combining stateful firewalling, DNAT/SNAT load balancing, and LRU state recovery into a single eBPF program offers incremental novelty over existing production and academic systems that already provide these capabilities or automate program merging without sacrificing NFV modularity, while the fixed 10-pattern exact-field matcher incurs up to 10 sequential hash lookups per packet (~250–295 ns) compared to single-lookup megaflow caches (Reference Paper: Cilium: eBPF-based Networking, Observability, and Security, Cilium Authors, 2025; Reference Paper: Verified Programs Can Party: Optimizing Kernel Extensions via Post-Verification Merging, Hsuan-Chi Kuo et al., 2022; Reference Paper: Domain Specific Run Time Optimization for Software Data Planes, Sebastiano Miano et al., 2022; Reference Paper: The Design and Implementation of Open vSwitch, Ben Pfaff et al., 2015; Reference Paper: Revisiting the Open vSwitch Dataplane Ten Years Later, William Tu et al., 2021).
* **State-Management and Concurrency Edge Cases in Control- and Data-Plane Logic:** When adding a port-specific IPv4 DROP rule ($m_3$–$m_5$, $m_8$), the control plane flushes existing connection entries in $\mathcal{T}_{fw}$, $\mathcal{L}$, and $\mathcal{T}_{rev}$ by matching only client-visible IP addresses (a superset of the rule), which can erroneously evict and break active connections on unrelated, permitted ports under a default-drop policy or when a backend is draining. In addition, the formal model and algorithms exhibit subtle edge cases when a new TCP SYN reuses a client port before prior state is reaped (matching $\mathcal{L}[f]$ in place on a draining backend and inheriting prior `FIN`/`RST` flags and creation timestamps) and during multi-syscall lockless updates to the active-backend list.
* **Emulated `veth` Testbed Limitations:** Because all experiments run over in-memory `veth` pairs within a single Mininet host kernel with checksum and segmentation offloads disabled, packets already carry an allocated `sk_buff` and execute in the sender's softirq context, which prevents evaluating native NIC driver-level XDP execution and causes the XDP hook to perform slower than TC.
* **Manuscript Revision Inconsistencies and Unresolved Placeholders:** The manuscript contains cross-section contradictions from an incomplete revision, including conflicting automated test counts between Section V-C (44 unit and 85 kernel tests, totaling 129) and the Abstract, Introduction, Section VI-A, and Conclusion (41 unit and 75 kernel tests, totaling 116), literal `TODOENTRIES` and `TODOSWEEP` placeholders in Section V-D, and a mismatch between the paired $t$-tests declared in Section V-D and the unpaired Welch $t$-tests reported in the Section VI narrative.

## Potential Issues And Suggestions
### [Framing, Positioning, Conclusion, and References] (Pages: 1-2, 11, 15)
#### Potential Mistakes and Improvements

1. **Characterization of Tuple Space Search vs. Fixed 10-Pattern Exact-Field Lookup (Abstract, Section II, and Section VII):**
   - **Potential Concern:** The Abstract (p. 1) and Section VII (Conclusion, p. 11) highlight that the per-packet cost with all ten rule patterns populated (`250–295 ns`) is *"independent of the number of rules (10–10 000),"* and Section II (*Kernel subsystems and classification*, p. 2) relates this matcher to Tuple Space Search (TSS) [19]. However, because the proposed matcher restricts policies to a fixed space of ten exact-match and all-or-nothing field-wildcard patterns (excluding arbitrary IP prefix lengths/LPM tries, which are deferred to future work in Section VII), its $O(1)$ scaling with respect to rule count holds specifically because rules cannot introduce distinct prefix-mask combinations beyond the ten predefined field masks. In general TSS (such as OVS's megaflow cache), rules with diverse prefix lengths spawn additional tuples and hash probes. Clarifying in Section II and Section VII that the constant 10-probe upper bound is a consequence of restricting rule expressiveness to exact field masks (without prefix wildcards) would make the complexity positioning more precise.

#### Minor Corrections and Typos

- **Page 1, Abstract:** The sentence *"All stateful configurations provide the required functions and spread load evenly, and all cost 13.6–26.9% of throughput relative to plain routing"* combines two distinct metrics under the word *"throughput."* Comparing this range against Section VI-C (p. 9) and Table IV (p. 10), the `13.6%` lower bound is the reduction in **64-byte UDP packet rate** for `TC+FIB` (`595 kpps` vs. `689 kpps`), whereas the `26.9%` upper bound is the reduction in **TCP byte throughput** for `nft+IPVS` (`9.49 Gbit/s` vs. `12.97 Gbit/s`; for TCP byte throughput alone, the reduction is `15.5–26.9%`). Rephrasing this in the Abstract as *"13.6–26.9% of throughput and packet rate"* (matching the phrasing in Section VI-C and Section VII) would avoid ambiguity.

### [Formal System Model & State Coupling Specification] (Pages: 2-4)
#### Potential Mistakes and Improvements

1. **Potential Concern: Asymmetry of the Immediate Bidirectional `DROP` Invariant Between VIP Traffic and Routed Traffic (Section III-D, page 3)**
   In Section III-D (page 3, right column), immediately following Eq. (5), the specification states:
   > *"An explicit DROP rule takes effect on the next packet in either direction, even on established connections; when one is added, the control plane additionally flushes the matching connection state."*

   A potential concern is that Eqs. (4) and (5) only guarantee immediate per-packet blocking in *both* directions for **load-balanced VIP traffic** (or symmetric address-pair rules such as $m_6, m_7$), where $\kappa(x)$ normalizes backend replies to the client-visible forward key $\kappa(x) = (d, v, p_d, p_v, \pi) = (c, v, p_c, p_v, \pi)$. For **routed traffic**, Section III-D notes that packets are *"matched in the orientation in which it travels"* ($\kappa(x) = f(x)$), and Eq. (5) evaluates $A(k)$ solely on $k = f(x)$, not on the reverse key $\bar{k} = \bar{f}(x)$. Consequently:
   - If an operator installs a directional IPv4 `DROP` rule matching one orientation of an established routed connection—such as $m_4: (s = c_1, d = s_2, p_d = 80, \pi = \text{TCP}) \mapsto \text{DROP}$ or $m_{10}: (d = s_2) \mapsto \text{DROP}$—a reply packet traveling in the opposite direction ($s_2 \to c_1$) has key $k = (s_2, c_1, 80, p_s, \text{TCP})$, which yields $A(k) = \text{NONE}$ rather than `DROP`.
   - Under $\delta = \text{ALLOW}$ (or if another rule admits the reverse orientation), packets in the reverse direction of the routed connection continue to be admitted by Eq. (5) even after $\mathcal{T}_{fw}$ is flushed. Even under $\delta = \text{DROP}$ with no reverse `ALLOW` rule, blocking the reverse direction of a routed flow relies on the user-space control plane having completed its asynchronous scan and flush of the shared entry in $\mathcal{T}_{fw}$ (so that $E(k)$ becomes $0$), rather than taking effect immediately through $A(k) = \text{DROP}$ on the very next packet in Eq. (5). Clarifying in Section III-D that directional `DROP` rules on routed traffic match in travel orientation—and block the opposite direction via state flushing only when $\delta = \text{DROP}$—would align the prose claim with Eqs. (4) and (5).

2. **Potential Concern: Stateful Admission of Non-SYN TCP Packets After Full Eviction or Expiry, and Unused "Seen a Reply" State (Sections III-D, III-E, III-F, and III-H, pages 3–4)**
   - **Non-SYN session creation and resurrection:** In Section III-D (Eq. (5)), an IPv4 packet matching an `ALLOW` rule (or `NONE` when $\delta = \text{ALLOW}$) is admitted unconditionally ($\text{adm}(x) = 1$) regardless of its TCP flags, and inserts a new entry into $\mathcal{T}_{fw}$ if neither $k$ nor $\bar{k}$ is present. Similarly, Section III-F states that *"A connection is lost only if both entries are lost before a packet rebuilds one, as with any NAT that loses state."* However, if both $\mathcal{L}[f]$ and $\mathcal{T}_{rev}[r(f)]$ for a TCP connection to a VIP are lost (either because both entries were evicted under LRU pressure while idle, or because the connection closed and expired after $T_{\text{fin}}$), a subsequent mid-stream or late non-SYN packet from the client will miss $\mathcal{L}[f]$, fail all $n$ recovery probes in $\mathcal{T}_{rev}[r_{b_i}(f)]$, and fall through to Eq. (6) (consistent with Algorithm 2, line 26) to allocate a new backend binding mid-stream (potentially picking a different backend if the pool changed or a backend drained) and instantiate fresh state in $\mathcal{L}$, $\mathcal{T}_{rev}$, and $\mathcal{T}_{fw}$ without a TCP SYN. Likewise, if $\mathcal{L}[f]$ expires slightly before $\mathcal{T}_{rev}[r(f)]$ on a closed connection, a late duplicate ACK or retransmitted FIN/ACK will hit $\mathcal{T}_{rev}$ and rebuild $\mathcal{L}[f]$ with a fresh creation time $\tau_c$, and every genuinely new UDP flow to a VIP unconditionally executes all $n$ failed recovery probes in $\mathcal{T}_{rev}[r_{b_i}(f)]$ before selecting a backend via Eq. (6) (as later noted in Section IV-F). Unlike standard stateful firewalls (`nf_conntrack`) and load balancers (IPVS) that require a TCP SYN by default to instantiate new TCP state, allowing arbitrary non-SYN packets to create state trades strict post-close/mid-stream rejection for transparent recovery after double LRU eviction. Explicitly noting these design trade-offs in Sections III-D–III-F would strengthen the formal specification.
   - **Role of the "seen a reply" mark and single-FIN half-close timeout:** In Section III-D (page 3, right column), the text specifies that *"A packet counts as a reply if it is a load-balanced reply by Eq. (4)—its key $k$ then hits the client's entry directly—or if only $\bar{k}$ is present (routed traffic); a reply marks the entry as having seen a reply."* However, neither the stateful admission indicator $E(k)$ in Eq. (5) nor the connection expiry condition in Eq. (9) references whether an entry has "seen a reply" ($E(k) = \mathbb{1}[\gamma = 1 \land (k \in \mathcal{T}_{fw} \lor \bar{k} \in \mathcal{T}_{fw})]$ treats an entry as established immediately upon the first admitted packet in either direction, and $\Theta(e)$ in Eq. (9) depends only on whether `FIN` or `RST` was seen). Clarifying whether the "seen a reply" mark is exported solely for observability/diagnostics or is intended to participate in timeout/eviction logic would eliminate a dangling state variable in the formal specification. Similarly, because each entry stores the union of TCP flags of both directions (Section III-D) and Eq. (9) sets $\Theta(e) = T_{\text{fin}}$ whenever `FIN` or `RST` has been seen in *either* direction, a TCP half-close (where one side sends `FIN` while the other continues sending data) immediately shortens the idle timeout to $T_{\text{fin}}$ ($5\text{ s}$) rather than waiting for bidirectional `FIN` closure; briefly noting this distinction from full TCP state machines in Section III-H would prevent ambiguity.

3. **Potential Concern: Non-Overlapping Pool Constraint Across Multiple VIPs (Sections III-E and III-F, pages 3–4)**
   - **Non-overlapping pool constraint across multiple VIPs:** Section III-F (*Isolation*) notes that *"A backend service endpoint $(a_b, p_b, \pi)$ belongs to exactly one service (the control plane rejects overlapping pools, per address, port and protocol)... Hence no un-translated connection can produce a key $r(f)$, and $\mathcal{T}_{rev}$ is injective."* It would be helpful to briefly note in Section III-E/F that because DNAT rewrites only the destination $(v, p_v) \to (a_b, p_b)$ and leaves the client source $(c, p_c)$ unchanged, this injectivity requirement precludes sharing the same backend daemon $(a_b, p_b, \pi)$ across two distinct VIPs (e.g., an internal and external VIP, or two VIP ports mapping to the same backend port), as their reverse keys $r_b(f) = (a_b, c, p_b, p_c, \pi)$ and endpoint index $\mathcal{E}[(a_b, p_b, \pi)]$ would otherwise collide.

### [Data-Plane Pipeline Algorithms, Hook Rewriting & Control-Plane Concurrency] (Pages: 5-7)
#### Potential Mistakes and Improvements

1. **Concurrency Hazards and Unspecified Fallback in `SELECT(f)` During Lockless Backend Draining and Restoration (Section IV-E and Algorithm 2)**
   - **Potential Concern:** Section IV-E (page 6, right column) describes the lockless sequence of separate `bpf()` map updates across `lb_backends` ($\alpha_j$), `lb_active` ($\lambda$), and `lb_services` ($n_{\text{act}}$): *"on a drain the backend's active flag is cleared first, then the list is rewritten, then $n_{\text{act}}$ is lowered; on a restore the new list entry is written before $n_{\text{act}}$ is raised. A concurrently running packet therefore never reads an unwritten list slot, and a stale slot that still names a drained backend is skipped because its flag is already clear."* Comparing this protocol against Eq. (6) and Algorithm 2 (`LOADBALANCE`, page 6, line 26) raises two potential specification gaps:
     1. **Unspecified fallback when encountering a cleared active flag ($\alpha_{j^*} = 0$):** Neither Eq. (6) ($j^*(f) = \lambda_{h(f) \bmod n_{\text{act}}}$) nor `SELECT(f)` in Algorithm 2 (line 26) specifies checking whether the selected backend's active flag $\alpha_{j^*}$ in `lb_backends` is 1 after indexing into `lb_active`, nor defines what fallback selection occurs to "skip" a stale slot if $\alpha_{j^*} = 0$ during the race window after $\alpha_j$ is cleared but before `lb_active` is rewritten and $n_{\text{act}}$ is lowered. If skipping means returning $\bot$ (line 27), a new connection arriving during that window is dropped; if it means probing for another active backend, that selection logic is omitted from Eq. (6) and Algorithm 2.
     2. **Transient array inconsistency during multi-syscall in-place shifts in `lb_active`:** Section III-E defines $\lambda = (\lambda_0, \dots, \lambda_{n_{\text{act}}-1})$ as the indices of active backends *in pool order*. When draining a backend at an intermediate position $k < n_{\text{act}} - 1$, shifting subsequent active indices left in `lb_active` element-by-element via separate `bpf()` calls while $n_{\text{act}}$ still holds its old value $M$ temporarily duplicates the last active backend at indices $M-2$ and $M-1$. Conversely, when restoring a drained backend into an intermediate pool slot (e.g., restoring slot 1 when active slots are $[0, 2]$ and $n_{\text{act}} = 2$), rewriting `lb_active` in pool order to $[0, 1, 2]$ before raising $n_{\text{act}}$ from 2 to 3 overwrites $\lambda_1 \leftarrow 1$ while $n_{\text{act}}$ is still 2, temporarily making active backend 2 unreachable for new connections until $n_{\text{act}}$ is raised (and the relative ordering of setting $\alpha_j \leftarrow 1$ on restore is not specified).
   - **Suggested Improvement:** Explicitly specify in Algorithm 2 and Section IV-E how `SELECT(f)` checks $\alpha_j$ and selects an alternative active backend when encountering $\alpha_j = 0$, and clarify the exact update sequence on restore (or note how packaging `lb_active` and $n_{\text{act}}$ into a single map value avoids multi-syscall array shift races).

2. **Potential Breaking of Unrelated Established VIP Connections Due to Address-Superset State Flushing on Port-Specific `DROP` Rules (Section IV-E)**
   - **Potential Concern:** Section IV-E (page 6, right column) states that adding an IPv4 `DROP` rule ($m_3$–$m_{10}$) iterates over $\mathcal{T}_{fw}$, $\mathcal{L}$, and $\mathcal{T}_{rev}$ and *"flushes the entries whose client-visible addresses match it (a superset when the rule also names ports)."* Because explicit `DROP` rules already take immediate precedence over established state on the very next packet in Algorithm 1 (line 19 via Eq. (5), where $A(k) = \text{DROP}$ yields $\text{adm}(x) = 0$ before $E(k)$ or `LOADBALANCE` is consulted), simultaneously flushing both $\mathcal{L}$ and $\mathcal{T}_{rev}$ using an address-only superset introduces a potential correctness concern for active, permitted load-balanced connections that share the same IP addresses on other ports or protocols (or flows exempted by a higher-priority `ALLOW` rule):
     - Suppose a client $c_1$ has an active TCP connection to VIP $(v, p_v = 80)$ assigned to backend $b_j$, and an operator adds a port-specific `DROP` rule such as $m_8: (d=v, p_d=8080, \pi=\text{TCP}) \mapsto \text{DROP}$ or $m_4: (s=c_1, d=v, p_d=22, \pi=\text{TCP}) \mapsto \text{DROP}$ (or adds a broad address `DROP` rule $m_9$/$m_{10}$ while a higher-priority `ALLOW` rule exempts $c_1 \to v:80$). Because the client-visible addresses match, an address-only superset flush deletes **both** $\mathcal{L}[f]$ and $\mathcal{T}_{rev}[r(f)]$ for the active connection on port 80.
     - As noted in Sections III-F and IV-E, losing both halves ($\mathcal{L}$ and $\mathcal{T}_{rev}$) of a load-balanced connection simultaneously is unrecoverable: if the next packet on the port 80 connection is a backend reply, `CLASSIFYREPLY` (Algorithm 1, line 14) will miss both $\mathcal{T}_{rev}$ and $\mathcal{L}$ and drop the legitimate reply via endpoint isolation (`kind = ISOLATE`); if the next packet is a client non-SYN packet, the 16-slot reverse-table recovery probe (Algorithm 2, line 22) will also miss and call `SELECT(f)`, which will remap and break the established connection if backend $b_j$ is currently draining ($\alpha_j = 0$) or the active pool has changed.
   - **Suggested Improvement:** Because the keys of $\mathcal{T}_{fw}$ and $\mathcal{L}$ and the key plus stored value $(v, p_v, \sigma, j)$ of $\mathcal{T}_{rev}$ already record the complete client-visible 5-tuple $(c, v, p_c, p_v, \pi)$, the control plane has all fields necessary to match the full rule predicate $m_i(\kappa(e))$ (and verify that $A(k) = \text{DROP}$ under the priority order) rather than flushing by addresses alone.

   - **Potential Concern:** Comparing the state-coupling specification in Sections III-D–III-H (pages 3–4) with Section IV-B (page 5) and Algorithm 2 (`LOADBALANCE`, page 6) reveals four closely related boundary cases when a client reuses an ephemeral source port $p_c$ to open a new TCP connection to the same VIP $(v, p_v)$—producing the identical 5-tuple $f = (c, v, p_c, p_v, \text{TCP})$—before prior state has expired or been reaped, or during forward-path eviction recovery:
     1. **New TCP `SYN` reusing a client port when $\mathcal{L}[f]$ is still present (Section III-E/F and Algorithm 2, line 17):** Sections III-E and III-F state that draining ($\alpha_j \leftarrow 0$) removes $b_j$ for new connections and that *"A SYN always opens a new connection, so it is placed by Eq. (6)"*, and Section V-C (page 7) lists a regression test for *"TCP SYNs that reuse a client port."* In the formal model and Algorithm 2, however, the check `if x is not a TCP SYN` only guards the eviction-recovery branch at line 22 (reached when $\mathcal{L}[f]$ is missing), whereas the primary lookup at line 17 (`if L[f] = (b, j) exists and b_j = b then`) matches unconditionally without checking whether $x$ is a TCP `SYN` or whether $\alpha_j = 1$. If a client closes a TCP connection and reuses the same source port to open a new connection to the same VIP before the user-space reaper deletes $\mathcal{L}[f]$ (up to $T_{\text{fin}} + 2\text{ s} = 7\text{ s}$), line 17 will route the new `SYN` in place to $b_j$ even if $b_j$ was placed into draining mode ($\alpha_j = 0$), contrary to the invariant that draining excludes $b_j$ for all new connections.
     2. **Inheritance of closed-connection `FIN`/`RST` flags and creation timestamps $\tau_c(e)$ (Sections III-D, III-H, and IV-B):** Sections III-D and III-H specify that each entry $e$ in $\mathcal{T}_{fw}$, $\mathcal{L}$, and $\mathcal{T}_{rev}$ stores creation time $\tau_c(e)$ and accumulates the union of TCP flags seen in either direction, applying the shortened idle limit $\Theta(e) = T_{\text{fin}}$ once `FIN` or `RST` has been recorded (Eq. (9).
     3. **Stale $\mathcal{T}_{rev}$ cleanup and coexistence of multiple reverse entries when a `SYN` selects a different backend (Section III-F and Algorithm 2, line 30):** Conversely, suppose $\mathcal{L}[f]$ from an earlier connection assigned to backend $b_{\text{old}}$ (at slot $i_{\text{old}}$) was evicted from $\mathcal{L}$ while $\mathcal{T}_{rev}[r_{b_{\text{old}}}(f)]$ remained present (or a new TCP `SYN` from a reused client port bypasses line 17), and `SELECT(f)` (line 26) assigns the new connection to a *different* backend $b_{\text{new}} \ne b_{\text{old}}$ (at slot $i_{\text{new}}$).      4. **Missing refresh of $\mathcal{T}_{rev}$ during forward-path eviction recovery (Algorithm 2, lines 22–24):** Section III-F states that *"Each packet therefore refreshes both entries and rebuilds a missing one from the other."* While normal forward hits (line 18) and reply processing (lines 3–4) refresh both $\mathcal{L}$ and $\mathcal{T}_{rev}$, the forward-path eviction recovery branch (lines 22–24) restores $\mathcal{L}[f] \leftarrow (b_i, i)$ upon hitting $\mathcal{T}_{rev}[r_{b_i}(f)]$ and returns immediately at line 24 without refreshing $\mathcal{T}_{rev}[r_{b_i}(f)]$ (omitting the update to its last-seen timestamp $\tau_\ell$ and TCP flags).
   - **Suggested Improvement:** Clarify in Sections III-E–III-H, Section IV-B, Algorithm 1 (line 27), and Algorithm 2 (lines 17, 23, and 30) that: (i) a new TCP `SYN` (without `ACK`) triggers fresh backend selection via `SELECT(f)` (at least when $\alpha_j = 0$ or `FIN`/`RST` has been seen), deletes any prior $\mathcal{T}_{rev}[r_{b_{\text{old}}}(f)]$ if a previous reverse entry existed for a different backend, and resets $\tau_c(e)$ and stored TCP flags in $\mathcal{L}$, $\mathcal{T}_{rev}$, and $\mathcal{T}_{fw}$; and (ii) line 23 of Algorithm 2 also refreshes $\mathcal{T}_{rev}[r_{b_i}(f)]$.

4. **First-Fragment Port Inspection, Rule Priority Ordering, and Non-First Fragment Endpoint Isolation (Sections III-C, III-D, III-F, Section IV-A, & Algorithm 1, Line 11)**
   - **Potential Concern:** By Section III-C (page 2), Section IV-A (*"Fragments"*, page 5, left column), and Algorithm 1 (page 5, right column, lines 1–13), every IPv4 fragment has $\rho(x) = 0$ (so its flow key in Eq. (1) is the port-less tuple $f(x) = (s, d, 0, 0, \pi)$), and the first fragment's transport ports $(p_s, p_d)$ are inspected solely at line 11 (`if x is a first fragment and its ports hit E or a port DROP rule then return DROP`). Three points across Sections III and IV in this logic warrant clarification:
     1. **Raw port extraction and bidirectional $\mathcal{E}$ check at line 11:** Because Eq. (1) defines $f(x)$ with $p_s = p_d = 0$ whenever $\rho(x) = 0$, a first fragment originating *from* a backend service endpoint $(s, p_s, \pi) \in \mathcal{E}$ has zeroed ports in $f$ when it reaches `CLASSIFYREPLY(f, \rho)` at line 14 and cannot be caught as `ISOLATE` at lines 15–16. For line 11 to enforce the bidirectional first-fragment isolation stated in Section III-F (*"the first fragment of a datagram to or from one"*), `PARSE(x)` must preserve the raw transport ports $(p_s, p_d)$ of a first fragment separately from $f$, and line 11 must check **both** the source tuple $(s, p_s, \pi) \in \mathcal{E}$ and destination tuple $(d, p_d, \pi) \in \mathcal{E}$.
     2. **Priority inversion between $m_8$ port `DROP` rules and higher-priority $m_6, m_7$ address `ALLOW` rules:** Section IV-A states that *"fragmented traffic needs an address-level rule"* (such as $m_6: (s, d, \pi)$ or $m_7: (s, d)$). Under the total priority order of Eqs. (2)–(3), address-level patterns $m_6$ and $m_7$ have **higher priority** than the port-specific pattern $m_8: (d, p_d, \pi)^\rho$. However, because line 11 unconditionally drops a first fragment matching *any* port `DROP` rule ($m_3$–$m_5, m_8$) before `adm(x)` is evaluated at line 19, a lower-priority $m_8$ `DROP` rule will override a higher-priority $m_6$ or $m_7$ `ALLOW` rule on fragmented traffic, inverting the priority order of Eq. (3).
     3. **Non-first fragments vs. *"admitted alike"* and endpoint isolation:** In Section III-D (Eq. (4)) and Section III-F (*Isolation* and *Coupling and recovery*), reply classification and service-endpoint isolation rely on looking up $\mathcal{T}_{rev}[f(x)]$ and $\mathcal{E}[(a_b, p_b, \pi)]$, both of which are keyed by the backend's transport port $p_b$. When a first fragment is dropped at line 11 (or when non-first fragments are sent directly to or from a backend service endpoint in $\mathcal{E}$), subsequent (non-first) fragments of the same datagram have $p_s = p_d = 0$, bypass line 11, cannot match $\mathcal{T}_{rev}$ or $\mathcal{E}$ in `CLASSIFYREPLY` (line 14), and return `NONE` at lines 7–8 of Algorithm 2 (`if \rho = 0 then return NONE`). Consequently, in Eq. (4), $\kappa(x)$ falls back to $f(x) = (a_b, c, 0, 0, \pi)$ rather than triggering service-endpoint isolation, exposing the backend's real address $a_b$ to address-level firewall rules ($m_6, m_7, m_9, m_{10}$) and, under $\delta = \text{ALLOW}$ or an address-level `ALLOW` rule, admitting those subsequent fragments at line 19 (creating port-less state $(s, d, 0, 0, \pi)$ in $\mathcal{T}_{fw}$ and incrementing `flow_stats` even though the first fragment was dropped). This qualifies the statements in Section IV-A that *"the fragments of one datagram are always admitted alike"* and in Section III-F that *"a backend's real address can never reach a client."*
   - **Suggested Improvement:** Clarify in Sections III-D, III-F, IV-A, and Algorithm 1 (line 11) that reply classification and $\mathcal{E}$-isolation require $\rho(x) = 1$, that `PARSE(x)` extracts raw first-fragment ports prior to zeroing $p_s, p_d$ in $f$ so line 11 probes $\mathcal{E}$ in both directions ($(s, p_s, \pi)$ and $(d, p_d, \pi)$), and that isolation of fragmented datagrams relies on dropping the first fragment so the receiver cannot reassemble the datagram (while considering respecting higher-priority $m_6$/$m_7$ `ALLOW` rules before applying an $m_8$ `DROP` rule at line 11).

2. **Incomplete Reporting of Microbenchmark Conditions and Shared-Metadata Tail-Call Ablation Variant Specified in Sections II, V-C, and V-D (Abstract, Section I-1, Section II, Section V-D, Section VI-E, and Section VII)**
   * **Observation:** Section II (Page 2), Section V-C (Page 7), and Section V-D (Page 8, right column) define several microbenchmark conditions and ablation variants that are omitted from Section VI-E, Table V, the Appendix figures (Figures 13–17), and the headline summaries:
     * *Shared-Metadata Tail-Call Ablation Variant (Section II and Experiment e):* In Section II (*Positioning*, Page 2), the manuscript notes that modular eBPF frameworks pass parsed metadata between chained stages instead of re-parsing packets from scratch, and states that the performance effect of merging network functions into one program is quantified *"with an ablation that chains the same stages by tail calls, both with re-parsing and with shared parse metadata (Section VI-E)."* Section V-C (Page 7, *"one equivalence test of both tail-call variants used in Section VI-E"*) and Section V-D(e) (Page 8, *"in two variants: each stage re-parses the packet, as in chained frameworks [9], or the stages share the parse result through a per-CPU map and the last stage only re-derives header pointers from stored offsets"*) likewise describe both variants.      * *DNAT Cost for a New UDP Flow (Experiment d):* Section V-D(d) states that the per-path microbenchmark measures *"DNAT of a new TCP connection and of a new UDP flow,"* and the caption of Figure 17 (Page 14) refers to *"a new connection (and a new UDP flow, where measured)."* This measurement directly corresponds to the algorithmic trade-off noted in Section IV-F (Page 6): because UDP lacks a SYN flag, *"every new UDP connection to a VIP pays these $n$ [$\le 16$ reverse-entry] probes; TCP SYNs skip them."* Yet Table V (`DNAT new`) and Figure 17 (`XDP new TCP` and `TC new TCP`) report only the new TCP connection cost and omit the new UDP flow cost.
     * *Intermediate Cache-Cold Flow Counts (Experiment c):* Section V-D(c) specifies measuring cache-cold state for *"1000, 15 000 and 60 000 tracked flows visited in random order, versus one flow (15 000 fits the 16 384-entry telemetry table, 60 000 does not)."* However, Section VI-E (*"Cache-cold state"*, Page 10) and Figure 15 (Page 14) report only the 1-flow and 60,000-flow endpoints, omitting the 1,000-flow and 15,000-flow intermediate points.
   * **Potential Concern:** Each omitted condition isolates a specific architectural mechanism claimed in the paper:
     1. *Overhead Attribution and Timing Baselines in Tail-Call Ablation:* Because modular frameworks such as Polycube [9] pass parsed metadata across stages via per-CPU maps rather than re-parsing headers at every tail call, reporting only the re-parsing variant conflates the intrinsic overhead of `bpf_tail_call` transitions with the cost of redundant three-stage packet parsing. Furthermore, the reported `33–47%` cost increase (`25–32%` savings) combines two different timing baselines from Table V: the `37%` increase (`27%` savings) on the `Pass` path comes from *repeat-loop* measurements (`93.3 ns` vs. `127.9 ns`), whereas the `33%` and `47%` increases (`25%` and `32%` savings) on the `DNAT est.` (`211.5 ns` vs. `280.5 ns`) and `SNAT est.` (`169.2 ns` vs. `249.3 ns`) paths are computed directly from raw *single-shot* measurements that include `60–80 ns` of per-syscall timing overhead in the denominator.

     3. *Cache Misses vs. Map Eviction Churn:* At 60,000 concurrent flows, the 16,384-entry per-CPU LRU `flow_stats` map undergoes continuous entry eviction and re-insertion on top of CPU cache misses; without the 1,000-flow and 15,000-flow data points (where all maps fit within capacity), it is not possible to separate hardware cache-miss latency on hash-table lookups from BPF LRU map eviction churn.
