# HIGH LEVEL SUMMARY

## Summary
This paper designs, formally specifies, implements, and evaluates an in-kernel Software-Defined Networking (SDN) gateway data plane written in eBPF and attachable at either the eXpress Data Path (XDP) or Traffic Control (TC) ingress hook. Rather than chaining separate network functions via `bpf_tail_call`, the proposed architecture consolidates packet parsing, a 10-pattern tuple-space stateful firewall, a Layer-4 Virtual IP (VIP) load balancer with bidirectional DNAT/SNAT and graceful backend draining, $O(1)$ incremental checksum maintenance, and per-flow telemetry into a single verified eBPF pipeline managed by a Python/libbpf control plane and connection reaper. The authors evaluate functional correctness across 116 automated unit and kernel tests and compare empirical performance in Mininet (`veth` topology) and via in-kernel `BPF_PROG_TEST_RUN` microbenchmarks against plain Linux routing, `nftables` with `nf_conntrack` and `IPVS`, stateless Open vSwitch (OVS), and OVS with connection tracking (`OVS-ct`).

## Strengths
* **Clean Formal Specification of Coupled Firewall and NAT State:** The paper presents a well-structured formal model where backend replies are pre-classified to reconstruct the client-visible VIP flow key $\kappa(x)$ prior to firewall admission, allowing a single VIP rule to govern both directions consistently while strictly isolating real backend endpoints. Furthermore, the mutual recovery mechanism between the forward (`lb_conntrack`) and reverse (`lb_reverse`) LRU hash maps effectively mitigates asymmetric entry eviction and user-space reaper race conditions.
* **Practical Single-Program Pipeline Consolidation:** Consolidating packet parsing, stateful firewalling, L4 load balancing, and telemetry into a single monolithic eBPF program avoids redundant header parsing and indirect branch overheads from `bpf_tail_call` chaining, saving 25–32% of per-packet execution time on pass and NAT paths while supporting both XDP and TC hooks from a unified codebase.
* **Rigorous Verification and Stateful Baseline Evaluation:** The implementation is thoroughly validated via 115 passing unit and in-kernel packet tests (independently verifying every rewritten checksum) alongside multi-round, CPU-pinned Mininet macrobenchmarks and `BPF_PROG_TEST_RUN` microbenchmarks that compare against stateful kernel baselines (`OVS-ct` and `nftables`+`IPVS`) rather than solely stateless forwarding.

## Weaknesses
* **Asymmetric Fast-Path Baseline Comparison (`TC+FIB` vs. Un-offloaded `nft+IPVS`):** The headline claim that the eBPF data plane with in-program FIB forwarding (`TC+FIB`, which uses `bpf_fib_lookup` and `bpf_redirect` to bypass the kernel IP routing stack) is 15.5–17.5% faster than the native Linux stack compares an ingress stack-bypass fast path against standard `nft+IPVS` traversing the full routing and Netfilter `FORWARD` hooks. The authors might consider evaluating or explicitly discussing Linux's native `nftables` software flowtable fastpath (`nf_flow_table`), which similarly offloads established conntrack/NAT flows at the ingress hook to bypass classic IP forwarding (Reference Paper: The eXpress Data Path: Fast Programmable Packet Processing in the Operating System Kernel, Toke Høiland-Jørgensen et al., 2018).
* **Incremental Architectural Novelty and Unmeasured Modular Frameworks:** Consolidating eBPF stages to avoid `bpf_tail_call` and re-parsing overheads is a well-documented optimization in the programmable data-plane literature, and the tail-call ablation attributes the 33–47% penalty (computed using inconsistent repeat-loop vs. single-shot denominators) to chaining without isolating redundant parsing or comparing directly against modular frameworks or bytecode-merging approaches (Reference Paper: A Framework for eBPF-Based Network Functions in an Era of Microservices, Sebastiano Miano et al., 2021; Reference Paper: Verified Programs Can Party: Optimizing Kernel Extensions via Post-Verification Merging, Hsuan-Chi Kuo et al., 2022).
* **Macrobenchmarks Restricted to Empty Rule Tables and Linear Pattern Scaling:** All end-to-end throughput and packet-rate macrobenchmarks in Table IV run with empty firewall rule tables—allowing the 10-bit pattern mask optimization to skip all ten hash lookups—whereas populating all ten patterns adds 150–220 ns per packet in microbenchmarks, which would noticeably impact end-to-end throughput compared to `OVS-ct`'s single-lookup megaflow cache (Reference Paper: Revisiting the Open vSwitch Dataplane Ten Years Later, William Tu et al., 2021).
* **Confounding of Cache-Miss Latency with Telemetry LRU Map Eviction Churn:** In the 60,000-flow cache-cold microbenchmark, the per-CPU `flow_stats` LRU map holds only 16,384 entries while the connection tables hold 65,536 entries, meaning over 72% of packets trigger expensive in-kernel BPF LRU map evictions and re-insertions rather than isolated hardware CPU cache read misses.
* **Underspecified Edge Cases in Formal State Coupling and Fragment Handling:** A few interactions between the formal model and the algorithm pseudocode would benefit from clarification, including how evicted reverse-NAT (`T_rev`) entries are re-inserted in Algorithm 2 without mutating state prior to firewall admission, how directional TCP flags are separated when VIP replies map to the forward key $k \in \mathcal{T}_{fw}$, and how IPv4 fragments ($\rho(x)=0$) interact with backend endpoint isolation ($\mathcal{E}$) and PMTUD ICMP errors.

### [Formal System Model, Stateful Admission, Load Balancing & NAT State Coupling (Section III)] (Pages: 2-4)
#### Potential Mistakes and Improvements

1. **Distinguishing Forward vs. Reply Directions in $\mathcal{T}_{fw}$ and Directional Rule Semantics Under $\kappa(x)$ Normalization (Section III-D)**
   - **Observation:** Section III-D states that *"Section III-F defines when a packet is a reply of a tracked connection"* and defines the firewall connection-tracking update as: *"the tracker refreshes the entry of $k$ if $k \in \mathcal{T}_{fw}$, otherwise that of $\bar{k}$ if present, and otherwise inserts $k$; a reply marks the entry as having seen a reply. Each connection thus occupies one entry, with one pair of timestamps and the TCP flags of both directions."*
   - **Potential Concern:** This specification leaves a subtle gap regarding how packet directionality is determined in $\mathcal{T}_{fw}$ and how directional rules behave across the two traffic classes:
     1. *Reply identification for routed vs. load-balanced flows:* Section III-F only defines reply classification for *load-balanced* connections (via $\mathcal{T}_{rev}$, $\mathcal{E}$, and $\mathcal{L}$). For ordinary routed (non-load-balanced) traffic, the condition under which a packet is treated as a reply by the firewall tracker—namely, when $k \notin \mathcal{T}_{fw}$ and the reverse key $\bar{k} \in \mathcal{T}_{fw}$—is left implicit. Conversely, for load-balanced traffic, Eq. (4) normalizes the rule key of a backend reply so that both client-to-VIP packets and backend-to-client replies evaluate to the exact same forward-oriented key $k = \kappa(x) = (c, v, p_c, p_v, \pi)$. Consequently, both directions of a load-balanced connection match the first branch ($k \in \mathcal{T}_{fw}$) directly rather than matching $\bar{k} \in \mathcal{T}_{fw}$ on the return path. Relying solely on whether $k \in \mathcal{T}_{fw}$ versus $\bar{k} \in \mathcal{T}_{fw}$ cannot distinguish server-to-client replies from client-to-server packets when recording directional TCP `FIN`/`RST` flags (Section III-F/III-H) or marking an entry as having seen a reply, unless the $\mathcal{T}_{fw}$ update explicitly uses the load-balancer reply classification (`kind = REPLY` in Algorithm 1) alongside the $\bar{k} \in \mathcal{T}_{fw}$ lookup hit.
     2. *Connection-oriented vs. packet-direction rule semantics:* Because $\kappa(x)$ maps both directions of a VIP connection to the single orientation $c \to v$, the IPv4 rule patterns $m_3$–$m_{10}$ act as connection-orientation predicates for VIP traffic (e.g., $m_9\text{: } (s = c)$ or $m_5$ matches both outbound client requests and inbound VIP replies, while $m_9\text{: } (s = v)$ matches neither), whereas they act as literal packet-direction predicates for non-VIP routed traffic. Furthermore, the statement that a single VIP rule covers both directions *"with or without connection tracking"* refers specifically to disabling the firewall's connection tracker ($\gamma = 0$, table $\mathcal{T}_{fw}$), whereas computing $\kappa(x)$ in Eq. (4) still relies on the load balancer's stateful connection tables ($\mathcal{T}_{rev}$ and $\mathcal{L}$).
   - **Suggested Improvement:** Explicitly specify in Section III-D that a packet is treated as a reply in $\mathcal{T}_{fw}$ if it is classified as a load-balanced reply by Eq. (4) (when $k \in \mathcal{T}_{fw}$) or if it matches the reverse key $\bar{k} \in \mathcal{T}_{fw}$ (for routed flows), clarify that *"without connection tracking"* refers to $\gamma = 0$ while LB state tracking remains active, and note the symmetry of $m_3$–$m_{10}$ across both directions of VIP flows.

2. **Interaction Between Backend Replacement/Removal and Bidirectional LRU State Recovery (Sections III-E, III-F, and Algorithm 2)**
   - **Observation:** Section III-E (*Stickiness and graceful draining*) specifies that for an established flow $f$ with $\mathcal{L}[f] = (b, j)$, the stored backend is reused as long as slot $j$ in $B_\sigma$ still holds $b$; *"Only if the backend was removed or replaced is $f$ re-selected; the old backend's reverse entry $\mathcal{T}_{rev}[r_{\text{old}}(f)]$ is deleted first."* Section III-F (*Coupling and recovery*) specifies mutual recovery when either $\mathcal{L}[f]$ or $\mathcal{T}_{rev}[r(f)]$ is lost to LRU eviction or a reaper race.
   - **Potential Concern:** Three edge cases arise in the interaction between backend pool modifications and asymmetric LRU eviction unless additional invariants are enforced:
     1. *Eviction of $\mathcal{L}[f]$ prior to in-place backend replacement:* When $\mathcal{L}[f] = (b_{\text{old}}, j)$ is present and the backend at slot $j$ was replaced, Algorithm 2 (Lines 18–19) explicitly deletes $\mathcal{T}_{rev}[r_{\text{old}}(f)]$ before selecting a new backend. However, if $\mathcal{L}[f] = (b_{\text{old}}, j)$ is evicted from $\mathcal{L}$ *before* slot $j$ in $B_\sigma$ is overwritten with a new backend $b_{\text{new}}$ (and the control plane does not proactively flush $\mathcal{T}_{rev}$ entries upon backend replacement), the next forward packet of $f$ bypasses the `L[f] = (b_old, j)` check (Algorithm 2, Line 18) and only probes $\mathcal{T}_{rev}[r_{b_i}(f)]$ for current pool members $b_i \in B_\sigma$ (Algorithm 2, Line 20), leaving the orphaned $\mathcal{T}_{rev}[r_{\text{old}}(f)]$ entry undeleted until reaper or LRU expiry. Conversely, if a lingering reply arrives from $b_{\text{old}}$ while $\mathcal{T}_{rev}[r_{\text{old}}(f)]$ is still present and $\mathcal{L}[f]$ is missing, the reply recovery rule (*"re-creating $\mathcal{L}[f]$ from $(\sigma, j)$ if missing"*, implemented in Algorithm 2, Line 3 as `L[g] <- ((s, p_s), j)`) re-creates $\mathcal{L}[f] = (b_{\text{old}}, j)$ without checking whether $B_\sigma[j]$ still holds $b_{\text{old}}$, causing the next forward packet to fail the $b_j = b$ check and re-select a backend mid-connection.
     2. *Positional slot indexing upon backend removal:* Section III-E defines $B_\sigma = (b_0, \dots, b_{n-1})$ of size $n \le 16$ and checks whether *"slot $j$ still holds $b$."* If removing a backend at index $i < j$ compacted $B_\sigma$, every surviving backend at index $j > i$ would shift to $j - 1$, invalidating $(b, j)$ for unaffected flows unless slot indices $j$ in `lb_backends` remain fixed upon deletion.
     3. *Ephemeral port reuse hitting stale $\mathcal{T}_{rev}$ entries:* If a connection closes without `FIN`/`RST` (e.g., UDP) and $\mathcal{L}[f]$ is evicted while $\mathcal{T}_{rev}[r_b(f)]$ remains in $\mathcal{T}_{rev}$ for a backend $b$ that has since begun draining ($\alpha_j = 0$), a subsequent new connection reusing the same client tuple $(c, v, p_c, p_v, \pi)$ will match the lingering $\mathcal{T}_{rev}[r_b(f)]$ entry during the forward recovery probe and be bound to the draining backend rather than selecting an active backend via Eq. (6).
   - **Suggested Improvement:** Clarify in Sections III-E, III-F, and IV-B the control-plane invariants when a backend is removed or replaced (whether matching $\mathcal{L}$ and $\mathcal{T}_{rev}$ entries are flushed or expire via the reaper/LRU, and whether slot indices $j$ remain fixed), and note that reply-side recovery requires $B_\sigma[j] = (a_b, p_b)$.

3. **Formal Signature of Rule Decision Notation $A(k)$ Under $\rho(x) = 0$ (Section III-C)**
   - **Observation:** Section III-C defines $\rho(x) = 1$ iff $x$ is TCP or UDP and is not an IPv4 fragment (neither More-Fragments nor fragment offset is set), setting $p_s = p_d = 0$ whenever $\rho(x) = 0$.
   - **Potential Concern:** In Eq. (3), the IPv4 rule decision is written as $A(k) = a(j^*, m_{j^*}(k))$, a function of the key $k$ alone, whereas the candidate pattern index set $I_4(x) = \{3, \dots, 10\} \setminus \{i : m_i \text{ requires } \rho \land \rho(x) = 0\}$ depends on the packet $x$ via $\rho(x)$.    - **Suggested Improvement:** Reflect the dependence on $\rho(x)$ in Eq. (3) (or include a brief forward reference in Section III-C to the fragmentation discussion in Section IV-A).

3. **Interaction Between IPv4 Fragment Handling ($\rho(x) = 0$), Backend Endpoint Isolation, Port-Specific `DROP` Rules, and PMTUD (Sections III-C, III-F, IV-A & Algorithm 2, Pages 2–5):**
   - *Potential Concern:* Section III-F (*Isolation*, p. 4) states the invariant that a backend service endpoint $(a_b, p_b, \pi)$ is reachable only through its VIP and that a packet addressed directly to a service endpoint is dropped. Section IV-A (*Fragments*, p. 4) specifies that the gateway does not reassemble IPv4 fragments and assigns $\rho(x) = 0$ (which zeroes $p_s = p_d = 0$ in $f(x)$ per Section III-C) to every fragment, including the first fragment carrying the L4 transport header. This creates three unaddressed edge cases:
     1. *Bypass of backend service endpoint isolation:* In Algorithm 2 (Lines 6–12, p. 5), `if \rho = 0 then return NONE` executes before the endpoint isolation check `if (d, p_d, \pi) \in \mathcal{E} then return DROP` (and similarly in `CLASSIFYREPLY`, where $p_s = p_d = 0$ when $\rho = 0$). If the firewall policy admits traffic to the backend host $a_b$ (either under a default action $\delta = \text{ALLOW}$ or via an address-level rule $m_6, m_7, m_9, m_{10}$ for non-VIP traffic), fragmented TCP or UDP datagrams sent directly to $(a_b, p_b, \pi)$ cannot match $\mathcal{E}[(a_b, p_b, \pi)]$ (where $p_b > 0$), bypass the $\mathcal{E}$ isolation check in `LOADBALANCE`, and are forwarded to the backend host, where its OS kernel reassembles them directly at the isolated service port $p_b$.
     2. *Port-specific `DROP` rules under $\delta = \text{ALLOW}$ and shared fragment state:* While Section IV-A notes that a port-specific rule admits only unfragmented traffic (implicitly assuming an `ALLOW` rule under $\delta = \text{DROP}$), under $\delta = \text{ALLOW}$ or alongside a broader address-level `ALLOW` rule, a port-specific `DROP` rule ($m_3, m_4, m_5, m_8$) is skipped when $\rho(x) = 0$, allowing fragmented traffic to bypass the port block.      3. *Path-MTU Discovery (PMTUD) across the VIP:* Section IV-A states that load-balanced services require unfragmented datagrams, which TCP guarantees through PMTUD and the DF flag. Because ICMP packets have $\rho(x) = 0$ and are matched only on outer $(s, d, \text{ICMP})$ (Section III-C), Algorithm 2 returns `NONE` at Line 7 without parsing the inner IPv4/TCP header embedded in the ICMP error payload to translate or forward it as a `RELATED` flow in $\mathcal{T}_{fw}$ or $\mathcal{T}_{rev}$ to the serving backend.
   - *Suggested Improvement:* Either parse L4 ports on first fragments ($\text{fragment offset} = 0$) for the endpoint isolation check $\mathcal{E}$ and `DROP` rules, or expand Sections III-C, III-F, and IV-A to explicitly document that endpoint isolation in $\mathcal{E}$ applies to unfragmented transport packets ($\rho(x) = 1$) and note the behavior of port-specific `DROP` rules and outer-header ICMP matching alongside items (i)–(iii).

4. **Forward-Path Recovery Loop Overhead on New Connections (Algorithm 2 & Section IV-F, Pages 5–6):**

5. **Control-Plane Concurrency, Reaper Deletion Ordering, and Wildcard/L2 `DROP` Flushing (Section IV-E, Pages 5–6):**
   - *Potential Concern:* Section IV-E (pp. 5–6) leaves three user-space synchronization details implicit where concurrency and data-structure layout affect consistency:
     1. *Reaper deletion order vs. single-half recovery:* Section IV-E (*Reaper consistency*, p. 6) explains that the user-space reaper re-reads each candidate immediately before deleting it, and argues that if a packet arrives during the remaining microsecond race window and "only one half of a load-balanced connection is deleted, the recovery rules of Section III-F rebuild it, including for draining backends; only the deletion of both halves loses the connection." If the user-space reaper deletes $\mathcal{T}_{rev}[r(f)]$ unconditionally as a coupled side effect of deleting an expired $\mathcal{L}[f]$ without independently re-reading and verifying $\tau_\ell$ of $\mathcal{T}_{rev}[r(f)]$, a packet arriving in that microsecond window would have both entries deleted back-to-back, preventing recovery. (Additionally, for non-VIP traffic relying on $\mathcal{T}_{fw}$ under $\delta = \text{DROP}$, state lives in a single table without a partner map to recover from.)
     2. *Non-atomic multi-map updates during drain/restore:* When a backend is drained or restored, user space updates the active backend index list $\lambda$ (`lb_active` array) and the active count $n_{\text{act}}$ in `lb_services` (Table I) via separate `bpf()` system calls. While the data plane executes Eq.    - *Suggested Improvement:* Clarify in Section IV-E (i) that the reaper independently re-reads and validates timestamps on both $\mathcal{L}[f]$ and $\mathcal{T}_{rev}[r(f)]$ before deleting each entry, (ii) the ordering of `bpf()` map updates when modifying `lb_active` and `lb_services`, and (iii) that connection-table flushing upon adding a `DROP` rule applies to IPv4 rules ($m_3$–$m_{10}$) via map iteration.

### [Experimental Setup, Baselines & Empirical Performance Analysis (Sections V & VI)] (Pages: 6-10)
#### Potential Mistakes and Improvements

1. **Confounding of CPU Cache-Miss Latency with Telemetry Map LRU Eviction Churn in the 60,000-Flow Microbenchmark (Section VI-E, Page 9):**
   - **Potential Concern:** In Section VI-E (*Cache-cold state*), the paper evaluates cache-cold performance by visiting 60,000 tracked flows in random order and reports that single-shot per-packet latency increases from $124\text{ ns}$ to $682\text{ ns}$ at XDP ($5.5\times$) and from $137\text{ ns}$ to $679\text{ ns}$ at TC ($4.9\times$). While the text notes in passing that *"in addition, the telemetry table holds only 16 384 flows, so most packets re-insert their telemetry entry,"* this map-capacity mismatch introduces a major confounding factor rather than a secondary effect.
   - **Explanation & Impact:** Because the connection-tracking maps (`fw_conntrack`, `lb_conntrack`, and `lb_reverse`) each hold 65,536 entries while the per-CPU `flow_stats` LRU hash map holds only 16,384 entries (Table I), cycling uniformly at random through 60,000 active flows exceeds the capacity of `flow_stats` by $3.66\times$. Consequently, approximately $72.7\%$ ($1 - 16,384 / 60,000$) of packets on established flows miss in `flow_stats` and execute a full in-kernel LRU eviction and hash-bucket insertion (`bpf_map_update_elem`) rather than an in-place 64-bit counter increment. As shown in Table V (`DNAT new` at $2,065\text{--}2,361\text{ ns}$ vs. `DNAT est.` at $211.5\text{--}240.3\text{ ns}$, where inserting into the four LRU hash tables adds $\sim 1.85\text{--}2.12\;\mu\text{s}$, or $\approx 460\text{--}530\text{ ns}$ per map insertion), BPF LRU map eviction and insertion are nearly an order of magnitude more expensive than a read lookup miss in LLC/DRAM. Therefore, the observed $\sim 550\text{ ns}$ penalty conflates hardware CPU cache (L2/LLC/DRAM) read misses across the connection tables with continuous software LRU eviction and insertion thrashing in the undersized `flow_stats` map.
   - **Suggested Improvement:** To isolate genuine hardware cache-miss latency on established-flow lookups from BPF LRU map eviction overhead, either increase the capacity of `flow_stats` to 65,536 entries (matching the connection-tracking tables) during the 60,000-flow random-access test, or report an additional random-access measurement across $\le 15,000$ concurrent flows (which exceeds L1/L2 cache capacity while fitting inside the 16,384-entry `flow_stats` table without triggering evictions). Additionally, explicitly noting that the $124\text{ ns}$ (XDP) and $137\text{ ns}$ (TC) cache-hot single-shot baselines correspond to the zero-rule configuration rather than the one-rule configuration of Table V ($155.7\text{ ns}$ and $173.0\text{ ns}$) would help readers cross-reference the text and table.

2. **Macrobenchmark Throughput and Packet-Rate Claims Restricted to Empty Firewall Rule Tables (Sections V-D, VI-C, VI-E, and VI-F, Pages 7–10):**
   - **Potential Concern:** As disclosed in Sections V-D, VI-C, and VI-G, all macrobenchmark throughput and packet-rate experiments in Table IV and Fig. 2 (except the single-rule UDP flood drop test) run with empty firewall rule tables (zero user rules), where the 10-bit populated-pattern mask allows the eBPF pipeline to skip all ten hash-table rule lookups ($0$ probes per packet, costing $74\text{--}100\text{ ns}$ in the repeat loop).
   - **Explanation & Impact:** Section VI-E (Fig. 3) shows that populating all ten rule patterns adds $150\text{--}220\text{ ns}$ per packet (increasing in-kernel execution time by $2.5\times\text{--}3.5\times$ to $250\text{--}295\text{ ns}$). At the 64-byte packet rates reported in Table IV ($488\text{--}601\text{ kpps}$, corresponding to a $\sim 1,660\text{--}2,050\text{ ns}$ average inter-packet budget), an extra $150\text{--}220\text{ ns}$ per packet represents roughly $8\text{--}13\%$ of total per-packet processing time. By contrast, Open vSwitch (`OVS-ct`) collapses multi-field OpenFlow rule classification and connection-tracking state into a single megaflow cache lookup after the first packet of a flow, and `nftables` evaluates established flows via a single early `ct state established accept` check after explicit drop rules. Thus, the headline conclusion that the eBPF data plane at TC is *"statistically indistinguishable from OVS with connection tracking and, with in-program forwarding, 16–18% faster than nftables with IPVS"* is only demonstrated under the degenerate zero-rule case (and the authors note in Section VI-C that before adding the empty-pattern skip optimization, every eBPF configuration was $10\text{--}19\%$ below `OVS-ct`).
   - **Suggested Improvement:** Include at least one macrobenchmark row or summary comparison in Section VI-C / VI-E (measuring routed and VIP TCP throughput and 64-byte UDP packet rate across `TC`, `TC+FIB`, `OVS-ct`, and `nft+IPVS`) with all ten rule patterns populated to directly quantify how the $150\text{--}220\text{ ns}$ tuple-space lookup cost translates into end-to-end performance relative to `OVS-ct` and `nft+IPVS`.

3. **Fast-Path Forwarding Asymmetry Between `TC+FIB` and the Native `nft+IPVS` Baseline (Abstract, Sections I, II, V-A, VI-C, VI-F, and VII, Pages 1, 2, 6, 8, and 10):**
   - **Potential Concern:** Across the Abstract, Section I (Contribution 4), Section II, Section V-A, Section VI-C, and Section VII, the paper frames its evaluation as a *"like-for-like comparison against the stateful alternatives available on the same kernel,"* highlighting that the `TC+FIB` configuration (which uses `bpf_fib_lookup` and `bpf_redirect` at the TC ingress hook to redirect packets directly to the egress interface, bypassing the Linux IP routing and forwarding stack) is $15.5\%$ faster in routed TCP throughput ($p < 0.001$) and $16.0\text{--}17.5\%$ faster in VIP packet rate and TCP throughput ($p < 0.001$) than `nft+IPVS`, whereas standard `TC` (without FIB redirect) passes packets to the standard Linux IP routing stack and is statistically indistinguishable from `nft+IPVS` on the routed path and in VIP packet rate.
   - **Explanation & Impact:** Linux's native `nftables`/`nf_conntrack` subsystem provides an architecturally analogous built-in fast-path mechanism—software flowtable offloading (`nf_flow_table`, configured via `flow add @...` at the Netfilter `netdev` ingress hook)—which caches established connection-tracking and NAT bindings at ingress and redirects packets via FIB lookup without traversing the classic IP forwarding path in the same manner as `TC+FIB`. Comparing an ingress stack-bypass fast path (`TC+FIB`) exclusively against un-offloaded full-stack `nft+IPVS` conflates the efficiency of the eBPF classifier/NAT pipeline design with the benefit of ingress stack-bypass forwarding.
   - **Suggested Improvement:** Either evaluate an `nftables` baseline with software flowtables enabled for a direct fast-path comparison against `TC+FIB` on the routed path, or explicitly acknowledge `nf_flow_table` in Sections II, V-A, VI-C, and VII to clarify that the native stack was evaluated on its standard forwarding path without ingress flowtable offloading (and note any architectural constraints regarding IPVS integration on the VIP path) so that gains from stack-bypass forwarding are cleanly distinguished from those of the eBPF policy engine.

4. **Inconsistent Baseline Denominators, Redundant Parsing, and Contextualization in the `bpf_tail_call` Ablation (Abstract, Sections I, II, V-D, VI-E, VII, Table V, Pages 1, 2, 7, 9, and 10):**
   - **Definitive Methodological Inconsistency in Percentage Denominators:** In the Abstract, Section I (Contribution 1), Section II, Section VI-E (*Tail-call ablation*, Table V), and Section VII, the paper contrasts its single-program design against modular, tail-call-chained frameworks such as Polycube [9] and bpf-iptables [14], reporting that splitting the pipeline into three chained programs (`XDP chain`) *"costs 35 ns (37%) more on the pass path and 69–80 ns (33–47%) more on the DNAT and SNAT paths"* (corresponding to the $25\text{--}32\%$ savings cited in Section I when using `XDP chain` as the denominator). In Table V, these percentages are computed against two incompatible denominators:
     - For `Pass`, the $+37\%$ increase ($34.6 / 93.3\text{ ns}$) is computed against the **repeat-loop** baseline ($93.3\text{ ns}$), which measures pure in-kernel execution time without system-call timing harness overhead.
     - For `DNAT est.` ($+32.6\%$, $69.0 / 211.5\text{ ns}$) and `SNAT est.` ($+47.3\%$, $80.1 / 169.2\text{ ns}$), the percentages are computed against the **single-shot** baselines, which *include* the $60\text{--}80\text{ ns}$ per-syscall timing harness overhead ($\approx 62.4\text{ ns}$ on the XDP `Pass` path, where single-shot is $155.7\text{ ns}$ vs. $93.3\text{ ns}$ in the repeat loop).
     Because constant syscall harness overhead cancels in the numerator difference ($\Delta$) but inflates the single-shot denominator, dividing by unadjusted single-shot totals understates the relative in-kernel overhead of tail-call chaining on the NAT paths (subtracting the $\approx 62.4\text{ ns}$ harness overhead from the single-shot denominators yields an in-kernel cost increase of $\approx 46\%$ for `DNAT est.` and $\approx 75\%$ for `SNAT est.`).
   - **Redundant Parsing, State Sharing, and Modular eBPF Context:** While Section II appropriately caveats that Polycube and bpf-iptables are not benchmarked directly because they differ in parsing, state layout, and rule semantics (e.g., Linear Bit Vector Search for arbitrary prefixes in bpf-iptables vs. a fixed 10-tuple exact-match space here), the headline claims in the Abstract, Contribution 1, and Conclusion attribute the 33–47% penalty to tail-call chaining without noting that each of the three tail-called programs (firewall, load balancer/NAT, telemetry) re-parses the packet headers from scratch (Section V-D(e)) rather than passing parsed metadata across stages via `xdp_md->data_meta` or per-CPU scratch maps. Moreover, in the monolithic pipeline (Algorithm 1), reply classification (`CLASSIFYREPLY`, which probes $\mathcal{T}_{rev}$ and $\mathcal{E}/\mathcal{L}$) executes *before* the firewall check to construct the client-visible key $\kappa(x)$, and its result is reused by `LOADBALANCE`; without inter-stage metadata passing, the NAT path in a strict `[firewall -> LB/NAT -> telemetry]` chain must either duplicate map lookups across stages or re-derive state, explaining why the chaining penalty on DNAT/SNAT ($69\text{--}80\text{ ns}$) is roughly double that of the pass path ($34.6\text{ ns}$). Additionally, recent eBPF compiler/runtime techniques mitigate modular chaining and static map-lookup overheads via post-verification bytecode merging (e.g., KFuse) and dynamic runtime specialization (e.g., Morpheus).
   - **Suggested Improvement:** Measure single-shot `Pass` for `XDP chain` in Table V (currently marked `n/m`), report both raw and harness-adjusted relative percentages for `DNAT est.` and `SNAT est.`, clarify in the framing and Section VI-E how much of the $35\text{--}80\text{ ns}$ penalty arises from `bpf_tail_call` dispatch itself versus redundant header parsing and duplicated map lookups, and briefly contextualize how modular frameworks share parsed metadata or apply runtime specialization/merging in Section II.

6. **Shared-Core Softirq Execution, SMT Reaper Contention, and Unpaired Statistical Testing on the Hybrid CPU Testbed (Sections V-B, V-D, VI-C, and VI-E, Pages 6–9):**
   - **Potential Methodological Concerns:**
     1. *Unpaired Welch's $t$-Test on a Paired Interleaved Block Design:* Section V-D explains that experiments are executed in 10 interleaved rounds—where each round runs all seven configurations once—specifically so that slow drift (e.g., thermal throttling on the laptop testbed) affects all configurations alike. However, the statistical comparisons between configurations use an unpaired two-sample Welch's $t$-test rather than a paired $t$-test matched by round. An unpaired test folds round-to-round drift back into the within-group variance (contributing to coefficients of variation up to $15\%$ and wide confidence intervals such as $10.16 \pm 1.07\text{ Gbit/s}$ for `TC`), reducing statistical power to separate configurations.
     2. *Same-Core Softirq and SMT Sibling Contention on a Hybrid CPU:* Section V-B notes that the Intel Core i7-1355U has 2 performance cores (P-cores, CPUs 0–3 across 2 physical cores with SMT) and 8 efficiency cores (E-cores, up to $3.7\text{ GHz}$). The client traffic generator is pinned to CPU 0 and the server to CPU 2, while the eBPF control-plane daemon and `ovs-vswitchd` are pinned to their SMT sibling threads (CPUs 1 and 3). Because Linux `veth` transmission executes the gateway's ingress data plane (`XDP`, `TC`, Netfilter, or OVS) synchronously in the sender's `NET_RX_SOFTIRQ` context on the same logical core (CPU 0 for forward traffic, CPU 2 for replies, as noted in Section VI-E), the traffic generator (performing software TCP segmentation with TSO and checksum offload disabled) and the gateway data plane compete for cycles on the same core. Furthermore, Section VI-E reports that a single reaper sweep over full tables takes $0.82\text{ s}$ out of every $2\text{ s}$ period on one core; if the reaper thread runs on CPU 1 during the 10-second `iperf3` benchmarks, it contends for P-core execution units and L1/L2 cache with CPU 0 via SMT, while any unpinned kernel background threads may be scheduled onto the slower E-cores.
   - **Suggested Improvement:** Clarify in Section V-D whether the user-space reaper thread on CPU 1 was active or paused during the 10-second `iperf3` runs (and how many connection entries were present in the maps during those runs), and whether E-cores were disabled or isolated. In addition, consider reporting paired $t$-tests (or confidence intervals on within-round pairwise differences) to leverage the interleaved block design.

7. **Incomplete Explanation of Identical Backend Connection Counts for `TC` and `TC+FIB` in Scenario T3 (Section VI-B and Table III, Page 8):**
