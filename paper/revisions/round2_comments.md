# HIGH LEVEL SUMMARY

## Summary
This paper designs, formally specifies, implements, and evaluates a single-program eBPF/XDP gateway data plane for Software-Defined Networking (SDN) that integrates a stateful firewall, a Layer-4 load balancer with DNAT/SNAT and graceful backend draining, incremental RFC 1624 checksum maintenance, and per-flow telemetry. Managed by a Python/libbpf user-space control plane with OpenFlow-style idle and hard connection timeouts, the pipeline evaluates firewall rules over the client-visible flow (resolving backend replies against the Virtual IP prior to firewall admission) and is benchmarked against native Linux routing, `nftables` with `IPVS`, and Open vSwitch (both stateless and with connection tracking, `OVS-ct`) across functional tests, Mininet emulated topologies, and in-kernel `BPF_PROG_TEST_RUN` scalability microbenchmarks.

## Strengths
* The paper provides a clean, unified mathematical specification (Equations 2–9) and a self-contained single-program eBPF pipeline that avoids tail-call chaining, formally specifying how pre-firewall reverse-NAT translation binds stateful admission strictly to the client-visible Virtual IP (VIP) so backend real addresses are not exposed.
* The experimental evaluation constructs a rigorous, reproducible "like-for-like" stateful comparison on the same kernel against both native Linux stateful subsystems (`nftables` + `IPVS`) and Open vSwitch with connection tracking (`OVS-ct`), using 93 automated unit/kernel tests and 10 interleaved, CPU-pinned benchmark rounds.
* The empirical analysis offers valuable systems insights by isolating the trade-offs between per-packet multi-table eBPF hash lookups and OVS's megaflow cache (which yields 10–19% higher bulk throughput for `OVS-ct` at the expense of 6x–8x higher first-packet upcall tail latency), while confirming $O(1)$ in-kernel per-packet execution cost up to 10,000 rules and 60,000 tracked connections.

## Weaknesses
* While the paper positions its monolithic, zero-tail-call pipeline against modular chained eBPF frameworks and prior eBPF stateful firewalls/load balancers, it omits empirical comparisons against eBPF baselines and relies on well-established primitives, making the architectural novelty incremental; the authors might consider benchmarking against modular eBPF baselines or a tail-call-chained ablation to quantify the consolidation gains (Reference Paper: A Framework for eBPF-Based Network Functions in an Era of Microservices, Sebastiano Miano et al., 2021; Reference Paper: Securing Linux with a Faster and Scalable Iptables, Sebastiano Miano et al., 2019; Reference Paper: The eXpress Data Path: Fast Programmable Packet Processing in the Operating System Kernel, Toke Høiland-Jørgensen et al., 2018; Reference Paper: Cilium: eBPF-based Networking, Observability, and Security, Cilium Authors, 2025).
* Because forward and reverse NAT states ($\mathcal{L}[f]$ and $\mathcal{T}_{rev}[r(f)]$) reside in separate LRU hash maps and the user-space reaper has a non-atomic check-then-delete race window, asymmetric LRU eviction or premature deletion of $\mathcal{L}[f]$ while a backend is draining ($\alpha_j = 0$) will cause Eq. (6) to skip the draining slot and remap an established connection, whereas eviction of $\mathcal{T}_{rev}[r(f)]$ during an asymmetric download causes backend replies to be evaluated against the backend's real IP rather than the VIP, leading to drops or un-SNATed address leaks.
* Because the pipeline does not reassemble IPv4 fragments or correlate inner ICMP payloads, the first fragment of a fragmented VIP datagram ($\rho(x) = 1$) undergoes DNAT/SNAT while subsequent non-first fragments ($\rho(x) = 0$) bypass NAT and port-based rules, preventing endpoint reassembly and breaking stateful admission under port-specific rules with a default-drop policy.
* All end-to-end macro-benchmarks are conducted over in-machine Mininet `veth` pairs with checksum and segmentation offloads disabled—which neutralizes native driver XDP's early-processing advantage due to `sk_buff`-to-`xdp_buff` conversion—and the primary bulk TCP and 64-byte UDP benchmarks use the direct $c_1 \rightarrow \text{gateway} \rightarrow s_2$ path rather than the VIP, bypassing the load-balancing and DNAT/SNAT rewrite stages.
* Please consider clarifying the formal directional semantics of the client-visible flow key $\kappa(x) = (v, c, p_v, p_c, \pi)$ on backend replies—where the VIP occupies the source fields rather than the destination fields matched by service rules like $m_8$—as well as the non-uniform load distribution produced by modulo linear probing (Eq. 6) when one or more backends are drained.

### [Formal System Model & Stateful Policy/NAT Specification] (Pages: 2-4)
#### Potential Mistakes and Improvements

1. **Directionality of the Client-Visible Flow Key $\kappa(x)$ vs. Bidirectional VIP Rule Semantics (Sections III-C and III-D, Eqs. (2)–(5))**
   - **Potential Concern:** For a backend reply packet $x$ with $f(x) = (a_b, c, p_b, p_c, \pi)$, Eq. (4) defines the client-visible flow key as $\kappa(x) = (v, d, p_v, p_d, \pi) = (v, c, p_v, p_c, \pi)$ when $\mathcal{T}_{rev}[f(x)] = (v, p_v)$. Immediately following Eq. (4), Section III-D states that *"Forward packets to the VIP already carry $(c, v, p_c, p_v, \pi)$. Hence rules written against the VIP apply in both directions,"* and the text following Eq. (5) states that *"An explicit DROP rule therefore takes effect immediately, even on established connections."* However, in $\kappa(x) = (v, c, p_v, p_c, \pi)$, the VIP endpoint $(v, p_v)$ occupies the *source* fields $(s, p_s)$ and the client endpoint $(c, p_c)$ occupies the *destination* fields $(d, p_d)$, whereas in forward packets $(v, p_v)$ occupies the destination fields. Because the IPv4 tuple patterns $m_3 \dots m_{10}$ in Eq. (2) are strictly directional, $A(k)$ in Eqs. (3) and (5) probes $\mathcal{R}$ using only $k = \kappa(x)$ (and not the reverse key $\bar{k}$), and Eq. (2) defines the dedicated service pattern $m_8: (d, p_d, \pi)^\rho$ (*"any client may reach $v:80/\text{TCP}$"*) without a symmetric source-service pattern $(s, p_s, \pi)^\rho$, any directional rule targeting the VIP as a destination ($m_3, m_4, m_6, m_7, m_8, m_{10}$ with $d = v$) matches $k$ only in the forward direction and yields $A(\kappa(x)) = \text{NONE}$ on reply packets:
     - *Stateless mode ($\gamma = 0$) under $\delta = \text{DROP}$:* When an `ALLOW` rule is written against a VIP destination (e.g., $m_8: (d = v, p_d = 80, \pi = \text{TCP}) \mapsto \text{ALLOW}$), forward packets match $A(k) = \text{ALLOW}$, while reply packets have $d = c \neq v$ and yield $A(\kappa(x)) = \text{NONE}$. When connection tracking is enabled ($\gamma = 1$), replies are admitted via the reverse lookup $\bar{k} = (c, v, p_c, p_v, \pi) \in \mathcal{T}_{fw}$ inside $E(k)$. However, when connection tracking is disabled ($\gamma = 0$, a supported configuration parameter in Table I and Section III-D) with $\delta = \text{DROP}$, $E(k) = 0$ and all backend replies are dropped despite the VIP `ALLOW` rule—and cannot be permitted by a symmetric service-port rule because Eq. (2) lacks an $(s, p_s, \pi)^\rho$ pattern.
     - *Interaction of directional `ALLOW` and lower-priority `DROP` rules ($\gamma = 1$):* In Eq. (5), established state $E(k)$ is consulted only when $A(k) = \text{NONE} \land \delta = \text{DROP}$, whereas $A(k) = \text{DROP}$ unconditionally returns $0$. If an operator configures a high-priority rule allowing client $c_1$ to reach the VIP (e.g., $m_4: (s = c_1, d = v, p_d = 80, \pi = \text{TCP}) \mapsto \text{ALLOW}$) alongside a lower-priority rule blocking unsolicited inbound traffic to $c_1$ (e.g., $m_{10}: (d = c_1) \mapsto \text{DROP}$), the forward packet matches $m_4$ (`ALLOW`) and populates $\mathcal{T}_{fw}$, but the reply packet $k = (v, c_1, 80, p_c, \text{TCP})$ misses $m_4$, matches $m_{10}$ (`DROP`), and is dropped despite belonging to an established connection ($E(k) = 1$).
     - *Immediate `DROP` enforcement on in-flight replies ($\delta = \text{ALLOW}$):* If an explicit `DROP` rule is written against the VIP destination (e.g., in $m_8$ or $m_4$) under $\delta = \text{ALLOW}$, Eq. (5) alone evaluates $A(\kappa(x)) = \text{NONE}$ and $\text{adm}(x) = 1$ on backend-to-client replies as long as $\mathcal{T}_{rev}[f(x)]$ remains present. In the implementation (Section IV-E), established connections are terminated because the user-space control plane proactively flushes matching entries from $\mathcal{T}_{fw}$, $\mathcal{L}$, and $\mathcal{T}_{rev}$ upon `DROP` rule insertion rather than solely through per-packet evaluation of Eq. (5).
   - **Suggested Improvement:** Clarify in Section III-D that $\kappa(x)$ constructs the reverse of the client-to-VIP 5-tuple so that $\bar{k} = (c, v, p_c, p_v, \pi)$ matches $\mathcal{T}_{fw}$ under stateful tracking ($\gamma = 1$), note the role of control-plane state flushing when destination-keyed `DROP` rules are added, and explain how directional VIP rules (such as $m_8$) behave when $\gamma = 0$ or when lower-priority destination `DROP` rules exist (or—if single VIP rules are intended to match both directions directly in $A(k)$—evaluate VIP rules against the canonicalized client-to-VIP direction or include a symmetric $(s, p_s, \pi)^\rho$ pattern in Eq. (2)).

2. **Asymmetric LRU Eviction and User-Space Reaper TOCTOU Race Hazards Between Coupled NAT Maps $\mathcal{L}[f]$ and $\mathcal{T}_{rev}[r(f)]$ (Sections III-D, III-E, III-F, IV-B, IV-E, Table I, Algorithm 1, and Algorithm 2)**
   - **Potential Concern:** Section III-F and Section IV-B specify that forward NAT state $\mathcal{L}[f]$ (`lb_conntrack`) and reverse NAT state $\mathcal{T}_{rev}[r(f)]$ (`lb_reverse`) reside in two separate 65,536-entry LRU hash maps so tables cannot fill up, relying on bidirectional traffic to maintain both entries: a forward packet refreshes $\mathcal{L}[f]$ and refreshes—or, if evicted, re-creates—$\mathcal{T}_{rev}[r(f)]$, while a reply refreshes both entries. Similarly, in Section IV-E ("Reaper consistency"), the authors analyze the microsecond-scale time-of-check to time-of-use (TOCTOU) window between the user-space reaper re-reading an idle map entry and deleting it, arguing that if a packet arrives in that window after a full idle period, *"the next forward packet re-creates the state, and re-selection yields the same backend as long as the pool is unchanged, because selection is a deterministic function of $f$."* Because eviction across the two separate LRU maps is independent and not atomic, and because reaper deletions remove both $\mathcal{L}[f]$ and $\mathcal{T}_{rev}[r(f)]$ (Section III-H), three edge cases are not fully covered by this coupling and recovery mechanism:
     - *Reaper race deletion or LRU eviction of $\mathcal{L}[f]$ during backend draining ($\alpha_j = 0$):* If an established connection's assigned backend $b_{j^*}$ has been placed into a draining state ($\alpha_{j^*} \leftarrow 0$), connection stickiness relies exclusively on $\mathcal{L}[f] = (b_{j^*}, j^*)$ persisting in `lb_conntrack` (Algorithm 2, Line 10). Furthermore, because $\mathcal{T}_{rev}[r(f)]$ stores only $(v, p_v)$ and omits the chosen backend slot index $j^*$ required by $\mathcal{L}[f] = (b_{j^*}, j^*)$ (Table I and Section III-F), a reply packet that hits $\mathcal{T}_{rev}[f(x)]$ can only refresh $\mathcal{L}[f]$ if it is still present (Algorithm 2, Line 3) and cannot re-create $\mathcal{L}[f]$ if it was evicted. If the reaper deletes $\mathcal{L}[f]$ during the TOCTOU window or if $\mathcal{L}[f]$ is evicted under LRU pressure during a server-to-client transfer while backend $b_{j^*}$ is draining ($\alpha_{j^*} = 0$), the next forward packet from the client will find $f \notin \mathcal{L}$, re-execute the new-connection probing loop of Eq. (6) (Algorithm 2, Lines 17–22), skip slot $j^*$ because $\alpha_{j^*} = 0$, and steer the active connection to a different backend—breaking per-connection consistency during graceful draining and, in the LRU eviction case, leaving the old $\mathcal{T}_{rev}$ entry undeleted (since stale reverse-entry deletion in Section III-E and Algorithm 2, Line 14 depends on $\mathcal{L}[f]$ existing).
     - *Eviction of $\mathcal{T}_{rev}[r(f)]$ or reaper race deletion followed by a backend reply:* While a forward packet hitting $\mathcal{L}[f]$ re-creates an evicted $\mathcal{T}_{rev}[r(f)]$ entry (Algorithm 2, Line 11), the converse does not hold on the reply path. If `lb_reverse` evicts $\mathcal{T}_{rev}[r(f)]$ under map pressure while $\mathcal{L}[f]$ remains present, or if the reaper deletes $\mathcal{L}[f]$ and $\mathcal{T}_{rev}[r(f)]$ during the TOCTOU window just before a backend-to-client reply $x$ arrives with $f(x) = f_{reply} = (a_b, c, p_b, p_c, \pi)$ (e.g., a response to the client packet that raced with the reaper, or a server push/keep-alive), then $f(x) \notin \mathcal{T}_{rev}$. In Algorithm 1 (Line 11), which executes prior to `LOADBALANCE`, $\kappa(x)$ by Eq. (4) falls back to the untranslated backend tuple $f(x) = (a_b, c, p_b, p_c, \pi)$ rather than the client-visible VIP key, and Algorithm 2 (Lines 1 and 6) misses $\mathcal{T}_{rev}$ and returns `NONE`. Under $\delta = \text{DROP}$ (without a rule allowing direct backend traffic), `adm(x)` (Line 12) drops the reply because $\mathcal{T}_{fw}$ only stores $(c, v, p_c, p_v, \pi)$ (and similarly for non-VIP traffic if $\mathcal{T}_{fw}$ is deleted just before a reverse-direction reply arrives). Under $\delta = \text{ALLOW}$ (or a broad subnet rule), Eq. (5) admits the packet, which then misses SNAT in the load balancer—exposing the backend's real address $(a_b, p_b)$ to the client—and when $\gamma = 1$, inserts $(a_b, c, p_b, p_c, \pi)$ into $\mathcal{T}_{fw}$ (Algorithm 1, Line 20). This violates the two invariants stated in Sections III-D and III-F that no firewall state is ever created for a backend's real address and that the client only ever observes the VIP.
   - **Suggested Improvement:** Discuss these asymmetric LRU eviction and reaper race boundary conditions in Sections III-F, IV-B, and IV-E to qualify that transparent state re-creation applies specifically to client-initiated forward packets when the assigned backend remains active ($\alpha_j = 1$). In addition, note that storing the backend slot index $j^*$ alongside $(v, p_v)$ in $\mathcal{T}_{rev}$ ($\mathcal{T}_{rev}[r(f)] = (v, p_v, j^*)$) would allow reply packets (which already carry $b = (a_b, p_b)$ in their source fields) to reconstruct an evicted $\mathcal{L}[f]$ entry symmetrically, that dropping or declining to track packets originating from configured backend service endpoints $(a_b, p_b)$ that miss in $\mathcal{T}_{rev}$ would preserve the firewall and VIP-isolation invariants even under $\mathcal{T}_{rev}$ eviction, and that in-kernel BPF timers (`bpf_timer`) could eliminate the user-space TOCTOU delete window.

3. **Non-Uniform Load Distribution Under Linear Probing When Backends Are Drained (Section III-E, Eqs. (6)–(7))**
   - **Potential Concern:** In Section III-E, a service pool $B_\sigma = (b_0, \dots, b_{n-1})$ of size $n$ assigns each new connection $f$ by hashing modulo the full pool size, $r = h(f) \bmod n$, and probing linearly in Eq. (6) for the first offset $k^*$ with $\alpha_{(r+k^*)\bmod n} = 1$. Immediately before Eq. (7), the text states: *"If $h$ is uniform, the number of connections $N_j$ received by each of $n$ active backends out of $N$ satisfies $\mathbb{E}[N_j] = N/n$, which we test with Pearson's statistic..."* This raises two concerns in the mathematical formulation:
     - The symbol $n$ is overloaded to denote the total pool capacity $|B_\sigma|$ in Eq. (6) and the number of active backends in Eq. (7).
     - Under the linear probing rule of Eq. (6), the uniform expectation $\mathbb{E}[N_j] = N / n_{\text{active}}$ holds only when all backends in the pool are active ($\alpha_j = 1$ for all $j \in \{0, \dots, n-1\}$). Whenever one or more backends are drained ($\alpha_r = 0$ while $r = h(f) \bmod n$ continues to partition the hash space into $n$ equal buckets), the entire $1/n$ traffic share of a drained slot $r$ is shifted onto its immediate active successor $(r + k^*) \bmod n$ rather than being redistributed evenly across all remaining active backends. For example, with $n = 4$ backends where $b_0$ is drained ($\alpha_0 = 0, \alpha_1 = \alpha_2 = \alpha_3 = 1$), $r \in \{0, 1\}$ both map to $b_1$, giving $b_1$ an expected $2/4 = 50\%$ of new connections while $b_2$ and $b_3$ each receive $25\%$.
   - **Suggested Improvement:** Distinguish the total pool size $n = |B_\sigma|$ from the number of active backends $n_{\text{act}} = \sum_{j=0}^{n-1} \alpha_j$, and clarify that Eq. (7) and the uniform expectation $\mathbb{E}[N_j] = N/n$ apply to the undrained state where all $n$ configured backends are active (noting the linear-probing skew onto adjacent slots when backends are drained).

4. **Domain and Pattern-Range Specification Between L2 Rules ($A_2(x)$) and IPv4 Rules ($A(k)$) in Eqs. (2), (3), and (5) (Sections III-C and III-D)**
   - **Potential Concern:** Section III-C defines a unified ten-pattern hierarchy in Eq. (2) where $m_1: (\text{mac}_s, \text{mac}_d)$ and $m_2: (\text{mac}_s)$ match Ethernet MAC addresses and $m_3 \dots m_{10}$ match IPv4/L4 fields $(s, d, p_s, p_d, \pi)$. Equation (3) then defines $A(k) = a(i^*, m_{i^*}(k))$ with $i^* = \min\{i : (i, m_i(k)) \in \mathcal{R}\}$ over a single argument $k$, and Section III-D evaluates Eq. (5) for IPv4 packets using the 5-tuple $k = \kappa(x) = (s, d, p_s, p_d, \pi)$ subject to $A_2(x) \neq \text{DROP}$. This introduces two specification ambiguities:
     - *Domain mismatch and $\rho(x)$ guard in Eq. (3):* Because $k = \kappa(x)$ in Eq. (4) is an IPv4 5-tuple that does not contain Ethernet MAC addresses, $m_1(k)$ and $m_2(k)$ are not well-defined on the domain of $k$ (they are functions of the Ethernet frame $x$ evaluated in $A_2(x)$). Furthermore, Eq. (3) does not explicitly restrict the minimization to exclude the $\rho$-annotated patterns $i \in \{3, 4, 5, 8\}$ when $\rho(x) = 0$.
     - *Semantics of L2 `ALLOW` rules on IPv4 traffic:* In Section III-D, an IPv4 packet is admitted iff $A_2(x) \neq \text{DROP}$ and $\text{adm}(x) = 1$ in Eq. (5). If $i^*$ in Eq. 5. **Scope of NAT, Stateful Firewalling, and Injectivity Invariants Under Fragmented IPv4 Traffic and Direct Backend Access (Sections III-C, III-D, III-F, IV-A, Algorithm 1, and Algorithm 2)**
   - **Potential Concern:**
     - *Inconsistent handling between first and non-first IPv4 fragments across stateful firewalling and NAT:* Section III-C defines $\rho(x) = 1$ iff $x$ is TCP or UDP and *not a non-first IPv4 fragment*, setting $p_s = p_d = 0$ otherwise, and Section IV-A ("Fragments") states that because the gateway does not reassemble IPv4 fragments, a *non-first* fragment has $\rho(x) = 0$, skips the port-based rule patterns, is matched on $(s, d, \pi)$, is tracked in $\mathcal{T}_{fw}$ under the zero-port key $(s, d, 0, 0, \pi)$, and is neither load-balanced nor NAT-rewritten. However, because the *first* fragment of a fragmented TCP or UDP datagram (where `Fragment Offset == 0` and the `More Fragments` (`MF`) flag is $1$) carries the L4 port header, it satisfies $\rho(x) = 1$. This creates three operational discrepancies between the first fragment and subsequent fragments of the same IPv4 datagram:
       1. *Partial NAT on Fragmented VIP Traffic:* For a fragmented TCP or UDP datagram sent to a VIP (or returned from a backend), the first fragment ($\rho(x) = 1$, keyed by $(s, d, p_s, p_d, \pi)$) matches in `LOADBALANCE` (Algorithm 2) and undergoes DNAT to $(a_b, p_b)$ (or SNAT back to $(v, p_v)$) and incremental L4 checksum update via Eq. (8) at Line 24 of Algorithm 1. Subsequent non-first fragments of the same datagram have $\rho(x) = 0$ (keyed by $(s, d, 0, 0, \pi)$), miss $\mathcal{T}_{rev}$ in Eq. (4) on the return path, hit Line 6 of Algorithm 2 (`if` $\rho(x) = 0$ `... return NONE`), and pass through untranslated, retaining the untranslated IPv4 destination $v$ (or source $a_b$). Because the first fragment and trailing fragments arrive with mismatched IPv4 addresses ($a_b$ vs. $v$), this exposes the backend's real address on replies and prevents recipient reassembly.
       2. *Dropped Non-First Fragments Under Port-Specific Rules with Default-Drop ($\delta = \text{DROP}$):* When a flow is permitted solely by a port-specific rule ($m_3, m_4, m_5,$ or $m_8$) under a default-drop policy ($\delta = \text{DROP}, \gamma = 1$), the first fragment ($\rho(x) = 1$) matches the rule and inserts the 5-tuple $(s, d, p_s, p_d, \pi)$ with non-zero ports into $\mathcal{T}_{fw}$ (Algorithm 1, Line 20). Subsequent non-first fragments have $\rho(x) = 0$: they skip all $\rho$-marked port patterns (yielding $A(k) = \text{NONE}$) and look up $k = (s, d, 0, 0, \pi)$ in $\mathcal{T}_{fw}$. 2. **In-Kernel Microbenchmark State Evolution, Cache Locality, and Single-Shot Timing Overhead (Sections V-D, VI-E, Fig. 4, and Table IV):**
   - **Potential Concern:** Several methodological details in the `BPF_PROG_TEST_RUN` microbenchmarks (Sections V-D and VI-E) represent potential concerns regarding how BPF map state and CPU caches behave across iterations:
     1. *Repeat-loop L1/L2 cache locality in the connection-scaling test (Fig. 4, right):* Benchmark (b) measures an admitted packet over the kernel's `repeat` loop ($2 \times 10^5$ runs per sample, 15 samples) with 0 to $60{,}000$ entries pre-populated in each connection table. Because `BPF_PROG_TEST_RUN` repeatedly executes the exact same packet buffer on a single core, the first iteration inserts or hits the flow key $k$ while the remaining $199{,}999$ iterations repeatedly hash to the exact same bucket and refresh the same map entry resident in the CPU's L1/L2 data cache, regardless of how many background entries occupy DRAM. While this confirms $O(1)$ algorithmic lookup complexity without hash-collision degradation at $91.5\%$ map occupancy ($60{,}000 / 65{,}536$), it measures cache-warm steady-state flow refreshes rather than cache-cold lookups or Last-Level Cache (LLC) miss penalties across tens of thousands of active concurrent flows.
     2. *State persistence across single-shot `DNAT` calls and single-shot harness overhead (Table IV):* Because in-place NAT modifies the packet headers on the first run, path-cost benchmark (c) times `Pass`, `DNAT`, and `SNAT` using single-shot invocations (`repeat = 1` across $20{,}000$ syscalls, 10 batch means) and estimates the incremental cost of `DNAT` ($61\text{--}71\text{ ns}$) and `SNAT` ($53\text{--}66\text{ ns}$) by subtracting the single-shot `Pass` time ($324.4\text{ ns}$ at XDP; $340.4\text{ ns}$ at TC). Second, the $109.1\text{--}119.3\text{ ns}$ gap between single-shot `Pass` and repeat-loop `Pass†` ($324.4\text{ ns}$ vs. $215.3\text{ ns}$ at XDP; $340.4\text{ ns}$ vs. $221.1\text{ ns}$ at TC) is nearly twice the inferred cost of the NAT rewrite itself and includes per-syscall harness setup as well as colder instruction/data cache and branch-predictor states across user-kernel boundary crossings, which may interact non-linearly with the extra map lookups (`lb_services`, `lb_backends`, `lb_conntrack`, `lb_reverse`) in the NAT paths.
     3. *Unconditional probing of all ten rule patterns at 0 rules (Fig. 4, left):* Section VI-E states that installing $10{,}000$ non-matching rules "forces all eight IPv4 rule lookups and both L2 lookups to miss," yielding virtually the same execution time as 0 installed rules ($214\text{ ns}$ vs. $215\text{ ns}$ at XDP; $234\text{ ns}$ vs. $221\text{ ns}$ at TC).
